---
title: Sz Props Basics
description: The sz prop object syntax — how to write Tailwind as JavaScript objects.
---

The `sz` prop lets you write Tailwind CSS as a JavaScript object. The build
plugin transforms it to a `className` string at compile time — zero runtime
cost for static values.

## Basic Usage

Every Tailwind utility has a corresponding sz prop key:

```tsx
// Tailwind string syntax
<div className="p-4 bg-blue-500 text-white rounded-lg" />

// Equivalent sz prop syntax — TypeScript validates each key and value
<div sz={{ p: 4, bg: 'blue-500', color: 'white', rounded: 'lg' }} />
```

Both produce identical HTML. In production, the classes are mangled to single
characters.

## Property Mapping

Tailwind class names map to camelCase sz prop keys:

| Tailwind class | sz prop               |
| -------------- | --------------------- |
| `p-4`          | `{ p: 4 }`            |
| `px-6`         | `{ px: 6 }`           |
| `bg-blue-500`  | `{ bg: 'blue-500' }`  |
| `text-white`   | `{ color: 'white' }`  |
| `rounded-lg`   | `{ rounded: 'lg' }`   |
| `font-bold`    | `{ weight: 'bold' }`  |
| `flex`         | `{ display: 'flex' }` |
| `hidden`       | `{ display: 'none' }` |

## One key per property

Props that set a single CSS property are written with their **canonical key and
a value** — one way, no aliases:

| CSS property         | sz key          | Example                                      |
| -------------------- | --------------- | -------------------------------------------- |
| display              | `display`       | `{ display: 'flex' }`, `{ display: 'none' }` |
| position             | `position`      | `{ position: 'absolute' }`                   |
| visibility           | `visibility`    | `{ visibility: 'hidden' }`                   |
| isolation            | `isolation`     | `{ isolation: 'isolate' }`                   |
| text-transform       | `textTransform` | `{ textTransform: 'uppercase' }`             |
| font-style           | `fontStyle`     | `{ fontStyle: 'italic' }`                    |
| font-smoothing       | `fontSmoothing` | `{ fontSmoothing: 'grayscale' }`             |
| text-decoration-line | `decoration`    | `{ decoration: 'underline' }`                |

```tsx
<div sz={{ display: "flex", position: "absolute", fontStyle: "italic" }} />
```

:::caution[Boolean sugar was removed]
Earlier versions accepted boolean aliases like `{ flex: true }`, `{ absolute: true }`,
`{ italic: true }`. These are **removed** — they emit nothing and warn in dev.
Use the canonical key above, or run `csszyx migrate` to rewrite them automatically.
Because each property has exactly one key, the same property can never be set
twice in one object.
:::

### True boolean utilities

Some utilities are genuinely on/off — not a value of a single property — and stay
boolean: composite helpers (`truncate`, `srOnly`), stackable font-variant-numeric
flags (`ordinal`, `tabularNums`), default-or-value toggles (`grow`, `ring`,
`blur`), and plugin components (`container`, `prose`).

```tsx
<div sz={{ truncate: true, tabularNums: true, grow: true, container: true }} />
```

## Type safety — unknown keys are caught by TypeScript

The `sz` prop type is **closed**: a key that isn't a known sz prop or variant is a
TypeScript error, so a typo or a legacy CSS-property name fails at compile time. Run
`tsc --noEmit` in CI to enforce it across a codebase.

```tsx
<div sz={{ bgColor: "red-500" }} /> // ❌ tsc error — unknown key; use { bg: 'red-500' }
```

For untyped `sz` (string keys, dynamic objects, or JS files) the build prints a
dev-mode warning instead — but lazily, only when a route is opened. To catch every
file at once, run the standalone scan, which reports each unknown/aliased key with
its `file:line` and exits non-zero so CI can gate on it:

```bash
npx @csszyx/cli check          # scan the whole project; no dev server needed
```

These dev-mode warnings print in Node contexts only — the build and SSR, never
the browser client. To keep the dev loop quiet and rely on `csszyx check` in CI
instead, mute them with `CSSZYX_QUIET_SZ_WARNINGS=1`:

```bash
CSSZYX_QUIET_SZ_WARNINGS=1 npm run dev   # no inline sz warnings; use `check` to audit
```

They stay on by default — an unknown key means a dropped class, a correctness
signal worth surfacing.

To deliberately use a brand-new Tailwind utility csszyx has no key for yet, opt out with
`@ts-expect-error` — a conscious decision; the runtime still emits the class:

```tsx
{
  /* @ts-expect-error - forward-compat utility not yet in csszyx */
}
<div sz={{ someNewUtility: "x" }} />;
```

Arbitrary variants are allowed by pattern (`@container`, `min-[320px]`, `[&>span]`).

## Does `sz` auto-type on a custom component?

**Only on host elements** (`<div>`, `<span>`, …). The JSX augmentation adds `sz` to
React's `HTMLAttributes` / `SVGAttributes`, so every DOM element accepts it. A custom
component has its own props type, so `sz` is **not** added there automatically.

Two separate layers, don't conflate them:

- **Compile** — the transform lowers `sz` → `className` on _any_ element, custom
  included: `<Card sz={{ p: 4 }} />` becomes `<Card className="p-4" />`. It works at
  runtime as long as `Card` forwards `className` down to a host element.
- **Type** — TypeScript checks the source _before_ the transform, so `<Card sz={…} />`
  is a type error unless `Card`'s props include `sz`.

Whether `sz` is typed depends on how the props are declared:

| `Card`'s props type                                     | `sz` typed?  |
| :------------------------------------------------------ | :----------- |
| `{ title: string }` (fresh type)                        | ❌ TS error  |
| `ComponentProps<'div'>` / `extends HTMLAttributes<T>`   | ✅ inherited |
| `{ title: string } & Pick<ComponentProps<'div'>, 'sz'>` | ✅ just `sz` |

The `Pick` form is the tidiest way to add `sz` to a fresh props type — no import, and
it tracks csszyx's own `sz` type:

```tsx
import type { ComponentProps } from "react";

type CardProps = { title: string } & Pick<
  ComponentProps<"div">,
  "sz" | "className"
>;

function Card({ title, sz, className }: CardProps) {
  // The transform rewrites `sz` → `className` before Card runs, so pick `className`
  // too and forward it onto the host element.
  return (
    <div sz={sz} className={className}>
      {title}
    </div>
  );
}
```

`Pick` only works when the augmentation is loaded (a `/// <reference types="@csszyx/types/jsx" />`
in scope, or the project's `csszyx-env.d.ts`) — otherwise `sz` is not a key of
`ComponentProps<'div'>`.

:::caution[Generic wrappers: declare `sz` directly, don't Pick]
Reserve the `Pick` recipe for **concrete** tags (`ComponentProps<'div'>`). On a
generic component (`<E extends ElementType>(props: BoxProps<E>)`),
`Pick<ComponentProps<E>, 'sz'>` distributes over every member of the
`ElementType` union — including SVG tags and `ComponentType`s that lack the
augmentation — and resolves **order-dependently**: deleting one unrelated file
can flip `sz` from optional to required across the codebase. Declare the prop
yourself instead; it is stable and also accepts `szv` factory output:

```tsx
import type { SzInput } from "csszyx";

type BoxProps<E extends ElementType> = { as?: E; sz?: SzInput };
```

:::

## Typing a component that forwards `sz`

csszyx exposes the `sz` value type from two places, for two different jobs:

- **`SzPropValue`** (`@csszyx/compiler`, re-exported by `@csszyx/types`) is what the
  JSX augmentation adds to host elements — the type of `sz` on `<div>`, `<span>`, ….
- **`SzInput`** (`@csszyx/runtime`) is what the runtime helpers (`szr`, `szcn`, …)
  accept — a wider union that also allows top-level `null` / `false` / `undefined`.

For a **wrapper component** that takes `sz` and forwards it onto a host element,
type the prop with the augmentation's type so it lines up with the element it
lands on:

```tsx
import type { SzPropValue } from "@csszyx/types";

function Box({
  sz,
  ...rest
}: { sz?: SzPropValue } & JSX.IntrinsicElements["div"]) {
  return <div sz={sz} {...rest} />;
}
```

Type the prop as `SzPropValue` and it forwards both ways: onto the host element
(same type) **and** into the runtime helpers, which accept it directly:

```tsx
import type { SzPropValue } from "@csszyx/types";
import { szr } from "@csszyx/runtime";

function Box({ sz, active }: { sz?: SzPropValue; active?: boolean }) {
  // `sz` flows into szr() without a cast, and onto <div> below.
  return <div sz={sz} className={szr(active && "ring-2")} />;
}
```

`SzPropValue` is assignable into the helpers' `SzInput`, so you no longer need a
cast or `@ts-expect-error` when a wrapper both forwards `sz` and calls `szr` /
`splitBoxSz`. Prefer `SzPropValue` at the JSX boundary; reach for `SzInput` only
when a value genuinely originates from the runtime side.

:::caution[Import the JSX augmentation exactly once]
`@csszyx/types/jsx` uses `declare module 'react'` to add `sz`. Import it from a
**single** global `.d.ts` (e.g. `src/csszyx-jsx.d.ts`), not per-component. Because
it is a global augmentation, whether TypeScript has pulled it into a given program
can shift which `@ts-expect-error` directives around `sz` are considered "used" —
adding an unrelated file can surface a `TS2578` at a previously-quiet site. Keeping
one import site keeps that deterministic.
:::

:::tip[Custom breakpoints are typed from your CSS]
Define a breakpoint once in Tailwind `@theme` and csszyx auto-generates the type — no
manual declaration:

```css
@theme {
  --breakpoint-tablet: 40rem;
}
```

```tsx
<div sz={{ p: 4, tablet: { p: 6 } }} /> // `tablet:` now type-checks + autocompletes
```

:::

## Nested Variants

Variants (hover, focus, responsive breakpoints) use nested objects:

```tsx
<button
  sz={{
    bg: "blue-500",
    color: "white",
    px: 4,
    py: 2,
    rounded: "md",
    hover: {
      bg: "blue-600",
    },
    focus: {
      outline: "none",
      ring: 2,
      ringColor: "blue-400",
    },
    disabled: {
      opacity: 50,
      cursor: "not-allowed",
    },
  }}
/>
```

## Responsive Breakpoints

Responsive modifiers are nested objects with the breakpoint as the key:

```tsx
<div
  sz={{
    w: "full", // width: 100% on mobile
    md: {
      w: "1/2", // width: 50% at md+
    },
    lg: {
      w: "1/3", // width: 33% at lg+
    },
  }}
/>
```

## Dark Mode

```tsx
<div
  sz={{
    bg: "white",
    color: "gray-900",
    dark: {
      bg: "gray-800",
      color: "white",
    },
  }}
/>
```

## Arbitrary Values

For one-off values not in the Tailwind scale, pass a string. The compiler
wraps it in `[...]` automatically:

```tsx
<div
  sz={{
    w: "333px", // w-[333px]
    bg: "#316ff6", // bg-[#316ff6]
    p: "1.25rem", // p-[1.25rem]
    top: "37px", // top-[37px]
  }}
/>
```

:::note[Arbitrary values]
For arbitrary values that look like fractions or Tailwind scale values,
use explicit units. `{ w: 4 }` → `w-4` (1rem), but `{ w: '4px' }` → `w-[4px]`
(exactly 4 pixels).
:::

## CSS Variables

Prefix any CSS custom property with `--` and the compiler wraps it in `(...)`:

```tsx
<div
  sz={{
    bg: "--my-brand-color", // bg-(--my-brand-color)
    color: "--text-primary", // text-(--text-primary)
    p: "--spacing-lg", // p-(--spacing-lg)
  }}
/>
```

:::caution[`--name` vs `--name(...)` — parens vs brackets]
A **bare** `--name` is a CSS variable → parenthesized `x-(--name)`. A
**`--name(...)`** with a call is a Tailwind **build-time function** (v4.3.2+)
→ bracketed arbitrary value `x-[--name(...)]`. The compiler picks the wrapper
from the value's shape, so you write neither in `sz`:

```tsx
<div
  sz={{
    bg: "--brand", // variable  → bg-(--brand)
    text: "--spacing(4)", // function  → text-[--spacing(4)]
    color: "--alpha(var(--brand) / 50%)", // function  → text-[--alpha(var(--brand)_/_50%)]
  }}
/>
```

This holds for **every** value position, not just the examples above. Do not add
your own `()` or `[]` — `{ bg: '--brand' }`, never `'(--brand)'` or `'[--brand]'`.
:::

## Arbitrary CSS (`css: {}`)

For CSS properties with no sz prop or Tailwind utility equivalent, use the
`css` escape-hatch. Keys are camelCase CSS properties; the compiler converts
them to `[prop:value]` arbitrary-property classes automatically.

```tsx
<div
  sz={{
    css: {
      writingMode: "vertical-lr", // [writing-mode:vertical-lr]
      touchAction: "none", // [touch-action:none]
      "--my-color": "red", // [--my-color:red]
    },
    hover: {
      css: { cursor: "crosshair" }, // hover:[cursor:crosshair]
    },
    md: {
      css: { writingMode: "horizontal-tb" }, // md:[writing-mode:horizontal-tb]
    },
  }}
/>
```

The `css` key accepts all `CSS.Properties` keys plus CSS custom properties (`--*`) — full IDE autocomplete and typo protection.

:::caution[Not a shortcut for standard props]
`css: {}` bypasses sz-layer mapping entirely. `{ css: { backgroundColor: 'red' } }` outputs `[background-color:red]`, not `bg-red`. Use `{ bg: 'red' }` for standard Tailwind utilities — only reach for `css: {}` when there is genuinely no sz prop for the property.
:::

## Conditional Values

Pass a ternary expression as any property value. When **both branches are static
literals** (string, number, boolean), the compiler compiles each branch at build
time and emits a conditional class expression — no CSS variables, no inline styles:

```tsx
<div
  sz={{
    bg: isActive ? "blue-500" : "gray-200",
    color: hasError ? "red-600" : "gray-900",
    scale: shrunk ? 75 : 100,
  }}
/>
// Compiler emits:
// className={`bg-blue-500 text-red-600 ${shrunk ? 'scale-75' : 'scale-100'}` …}
// (each ternary prop compiled independently, static props merged into a single string)
```

:::note[When does the CSS variable fallback apply?]
Only when at least one branch is a **runtime expression** (variable, function call, etc.).
In that case the compiler falls back to `prop-[var(--_sz-prop)]` with an inline `style`.

If the opposite branch is `undefined`, `null`, `false`, or an empty string, that
branch emits neither the utility class nor the CSS custom-property value. This
keeps nullable values from becoming strings such as `"undefined"`. Numeric `0`
is not treated as absent—it remains a valid value.

```tsx
<div sz={{ flex: typeof flex === "number" ? flex : undefined }} />
// present: flex-(--_sz-flex) + --_sz-flex: <number>
// absent:  no flex utility and no --_sz-flex value
```

Keys whose value is a **boolean** are the exception — `border` and every side,
`ring`, `outline`, `shadow`, `truncate`. They toggle a bare class rather than
carrying a value, so a runtime value on them compiles to a conditional class
instead of a CSS variable. React discards booleans in `style`, and the valued
utility means something else anyway (`border-b-(--var)` is a border *color*,
while `border-b` is a *width*):

```tsx
<div sz={{ borderB: isOpen }} />
// → className={__szBoolClass(isOpen, "borderB", "border-b")}
// true → "border-b"; false/null/undefined/"" → no class, silently
// any other type → the class is omitted and csszyx warns, because the value
// cannot mean anything here
```

When the generated CSS variable sits beside one direct object-literal JSX prop
spread—or one conditional whose branches are object literals—the compiler
injects it into every branch's `style`. This preserves authored style without
evaluating the spread expression twice:

```tsx
<div sz={{ w: width }} {...(cond ? { style: { flex } } : {})} />
// → {...(cond
//   ? { style: { flex, "--_sz-w": __szSpacingVar(width, "w") } }
//   : { style: { "--_sz-w": __szSpacingVar(width, "w") } })}
```

Unresolved spreads (`{...props}`), multiple spreads, and object branches with
their own unknown spreads retain the collision diagnostic. Move their style to
an explicit `style={...}` prop so the compiler can merge it without guessing
about evaluation or precedence.

The injected value resolves at runtime the same way the static path lowers the
same literal: numbers ride the spacing scale (`calc(n * var(--spacing))`),
tokens resolve to their CSS values (`'full'` → `100%`, `'3/12'` → `25%`,
`'screen'` → `100vw`/`100vh` per axis), and raw lengths/keywords
(`'100%'`, `'max-content'`) pass through — so a prop typed to the same union
as the static form works with any of its values at runtime.
:::

Works inside variant blocks too:

```tsx
<div
  sz={{
    p: 4,
    hover: { scale: isHovered ? 110 : 100 },
  }}
/>
// hover branch: hover:scale-110 or hover:scale-100 — zero runtime
```

### Conditioning the whole `sz`, not one value

The same applies one level up. `sz={cond ? A : B}` compiles both branches to
class strings, and a branch that styles nothing — `undefined`, `null`, `false`,
or `{}` — is the **empty style**, not an unknown one, so it compiles too:

```tsx
<div sz={disabled ? { color: "muted" } : undefined} />
// → className={disabled ? "text-muted" : undefined}
```

A guard is the same expression with the else arm left off, so it compiles the
same way:

```tsx
<div sz={compact && { p: 2 }} />
// → className={compact ? "p-2" : undefined}
```

`||` is deliberately left on the runtime path. It yields its **left** operand
when the test passes, and that value can itself be a style — folding
`sz={base || { p: 4 }}` would drop `base` — so it keeps `_sz()`.

Two shapes still resolve at runtime: a chain of tests (`a ? x : b ? y : z`), and
a branch holding a value only the runtime knows (`cond ? { p: pad } : undefined`).

## Array Syntax

Pass an array to `sz` to compose styles with **later-wins** semantics: when two
elements touch the same property, the later element's value overrides the
earlier one's — like `Object.assign`, and like every class-merge tool you know.
Elements can be sz objects, class strings, `cond && …` guards, or runtime
values (a forwarded [`szsc`](/docs/compound-components/#the-szs-prop--style-internal-parts-in-one-prop)
slot).

```tsx
// Fully static — deep-merged at build, compiled to ONE className, zero runtime
<div sz={[{ text: 'base', p: 4 }, { text: 'lg' }]} />
// → className="text-lg p-4"           (text-lg overrode text-base)

<div sz={[{ hover: { bg: 'red-500' } }, { hover: { p: 2 } }]} />
// → className="hover:bg-red-500 hover:p-2"   (deep merge: siblings survive)

// Anything else — composed at runtime (same later-wins rule, applied per
// property group, mangle-safe). The compiler injects `_szcn`, a generated
// helper you never write by hand (the `_` marks compiler-injected code):
<div sz={[
  { p: 4, color: 'white' },
  isActive && { bg: 'blue-500' },
  szsc?.title,                      // dynamic element via _szPart
]} />
// → className={_szcn("p-4 text-white", isActive && "bg-blue-500", _szPart(szsc?.title))}

// Finite ternaries compile to class strings instead of deferring objects to _szPart:
<a sz={[
  { decoration: 'none' },
  disabled ? { color: 'muted' } : { color: 'main' },
  szsc?.link,
]} />
// → className={_szcn("no-underline", disabled ? "text-muted" : "text-main", _szPart(szsc?.link))}

// Falsy property branches contribute no utility token (never `flex-undefined`):
<div sz={[{ decoration: 'none', flex: fluid ? 1 : undefined }, szsc?.root]} />
// → className={_szcn("no-underline", fluid ? "flex-1" : "", _szPart(szsc?.root))}
```

This makes `sz={[defaults, override]}` the one-liner for slot defaults in a
compound component — no `className` plumbing, no manual `szcn` call:

```tsx
function Card({ title, szsc }: SzsProps<"title"> & { title: string }) {
  return (
    <h3 sz={[{ weight: "semibold", text: "base" }, szsc?.title]}>{title}</h3>
  );
}
```

Array syntax is especially useful with [`szv()`](/docs/szv) variant objects:

```tsx
import { szv } from "csszyx";

const btn = szv({
  base: { px: 4, py: 2, rounded: "md" },
  variants: { intent: { primary: { bg: "blue-600", color: "white" } } },
});

<button sz={[btn({ intent: "primary" }), isLoading && { opacity: 50 }]} />;
```

:::note[Falsy values]
Inside an array, `false`, `null`, `undefined`, and `0` are silently skipped —
only truthy objects contribute classes.
:::

:::note[An empty `sz` renders no `class` attribute]
A **statically lowered** `sz` that resolves to zero classes — `sz={{}}`,
`sz={[]}`, or the empty branch of a conditional like `sz={cond ? { pl: 4 } : {}}`
— now compiles to `className={undefined}` (or `className={cond ? "pl-4" :
undefined}`), so the framework omits the `class` attribute entirely instead of
emitting `class=""`. This holds on both artifacts of the
engine (native and wasm).

One case still emits `class=""`: a conditional that **can't be lowered at build
time** (for example a dynamic ternary whose value isn't statically resolvable)
falls back to a runtime `szr(…)` call, which returns `""` for an empty result.
That is harmless but noisy; to drop the attribute there, render the two cases as
separate elements so the styleless one carries no `sz` prop at all (e.g. SolidJS
`<Show>` with a `fallback`).
:::

:::caution[Keep conditional branches statically resolvable]
Tailwind only emits CSS for classes the compiler can see at build time. Inline
object literals and same-file `const` bindings are resolved statically — every
branch lands in the Tailwind safelist even if it never renders during the
build. **Imported objects and member access** (`styles.active`,
`variants[kind]`) cannot be resolved: those elements fall back to runtime
`_sz()` and their classes are **missing from the generated CSS** — the markup
renders with class names that have no selector.

```tsx
// ✅ statically discoverable — both branches reach Tailwind
const active = { bg: 'blue-500' } as const;
<div sz={[{ p: 4 }, isActive && active]} />
<div sz={{ p: 4, ...(isActive ? { bg: 'blue-500' } : { bg: 'gray-100' }) }} />

// ❌ NOT discoverable — bg-blue-500 ships without CSS
import { variants } from './styles';
<div sz={[{ p: 4 }, isActive && variants.active]} />
```

For style maps keyed at runtime, use [`szv()`](/docs/szv) (variants are
declared statically) or [`dynamic()`](/docs/dynamic) (injects CSS at runtime).

csszyx reports both shapes while it builds. When the value comes from an
**import**, that report is kept in **production** builds too and survives
`quiet: 'nudges'` — the compiler went looking for a module-level value, could
not read it, and no class was collected anywhere, which is a build result
rather than style advice. Reading imported objects is on by default
([`build.importedStaticSz`](/docs/reference/config/#imported-static-sz-objects-importedstaticsz)),
so the report means the import did not qualify — or that the setting was
turned off.

Every other unresolved shape stays advisory and dev-only, including a
forwarded prop:

```tsx
// Advisory: `sz` belongs to the CALLER, whose literal is collected where it
// is written. Forwarding it this way is the supported wrapper pattern.
function Box({ sz }: { sz?: SzPropValue }) {
    return <div sz={sz} />;
}
```
:::

## Shared Style Objects

Pass a variable directly to `sz` when no properties need overriding — the
compiler resolves it at build time just like an inline object:

```tsx
const item = { p: 3, rounded: "md", bg: "white" } as const;

<div sz={item} />; // → className="p-3 rounded-md bg-white"
```

Use object spread (`sz={{ ...var, ... }}`) only when you need to **override or
add** properties. Last key wins:

```tsx
const card = { p: 6, rounded: 'xl', shadow: 'md' } as const;

<div sz={{ ...card, p: 4 }} />          // p: 4 overrides card's p: 6
<div sz={{ shadow: 'sm', ...card }} />  // card's shadow: 'md' wins
```

Multiple spreads and nested variant objects are also resolved statically at
build time:

```tsx
const layout = { display: "flex", gap: 4 };
const colors = { bg: "blue-500", color: "white" };

<div sz={{ ...layout, ...colors, hover: { opacity: 75 } }} />;
// → className="flex gap-4 bg-blue-500 text-white hover:opacity-75"
```

### Conditional Spread with Static Overrides

When the _base_ style depends on a runtime condition but additional properties
are fixed, spread the ternary inline. The compiler hoists the condition outward
and resolves each branch separately — still zero runtime cost:

```tsx
const active = { bg: "blue-500", color: "white" } as const;
const inactive = { bg: "gray-100", color: "gray-600" } as const;

// rotate is always 45 — compiler emits: isActive ? "bg-blue-500 text-white rotate-45" : "bg-gray-100 text-gray-600 rotate-45"
<div sz={{ ...(isActive ? active : inactive), rotate: 45 }} />;
```

This works as long as:

- **Exactly one** conditional spread (`...(cond ? a : b)`)
- The **static overrides** are compile-time values (literals, variables)

When either condition isn't met, the compiler falls back gracefully (see below).

:::caution[Graceful fallback — but classes skip Tailwind]
Spreads that can't be fully resolved at build time — imported variables,
function calls, or multiple conditional spreads — fall back to `_sz()` at
runtime. The element still renders correct class names, but **those classes
never reach the Tailwind safelist**, so no CSS is generated for them unless
the same classes also appear statically elsewhere. In development, the
compiler emits a build-time warning explaining why the fallback occurred and
suggesting the right alternative (`szv()` for static variants, `dynamic()`
for runtime data).
:::

## Combining with className

The `sz` prop and `className` prop can coexist. The compiler merges them:

```tsx
<div sz={{ p: 4, bg: "blue-500" }} className="custom-class" />
// → className="p-4 bg-blue-500 custom-class"
```

When `className` is a dynamic expression (not a static string), the compiler
uses `_szMerge` at runtime to join them safely:

```tsx
// className is dynamic → _szMerge at runtime
<div sz={{ p: 4 }} className={baseClass} />
```

## Runtime Helpers for Dynamic Classes

When class names depend on runtime values, use the helper functions:

```tsx
import { _sz } from 'csszyx';

// Concatenate multiple class strings
<div className={_sz('p-4 bg-blue-500', extraClass)} />

// Conditional: plain JS conditionals compose with _sz
<div className={_sz('base', isActive && 'ring-2 ring-blue-400')} />

// Switch: a plain object lookup
<div className={{
  primary: 'bg-blue-600 text-white',
  danger:  'bg-red-600 text-white',
}[variant] ?? 'bg-gray-500 text-gray-900'} />
```
