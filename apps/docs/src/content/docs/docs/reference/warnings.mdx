Every message csszyx prints is listed here with its exact wording, so you can
paste a line from your terminal or console into <kbd>Ctrl</kbd>+<kbd>F</kbd> and
land on the row that explains it.

Placeholders are written the way the source writes them — `{filename}`,
`{key}`, `{n}` — and are filled in at emit time.

## How to read a csszyx message

Every message starts with `[csszyx]`. Two things decide where it shows up and
whether you can ignore it:

- **Where it runs.** *Build* messages come from the bundler plugin, the
  compiler, or the CLI, and appear in the terminal. *Runtime* messages come from
  the runtime helpers and appear in the browser console (or the SSR terminal).
- **What it costs.** Some messages report that **CSS is missing** from the
  output. Others are **usage advice** — the styles are fine, the code could be
  better. csszyx treats those two very differently.

### Anatomy of a fallback line

The most common build message has a fixed shape:

```text
[csszyx] {module}:12:9
  sz fallback at 12:9: identifier `cardStyles` could not be resolved to a static value.
  Suggestion: make it a module-level or function-body `const` with a literal object value; for variant-based styling use `szv()`, for runtime values `dynamic()`.
```

| Part | Meaning |
| --- | --- |
| `{module}:12:9` | The module the bundler named, such as `/src/components/Card.tsx`, and the line and column the engine placed the finding at. Every `sz` build diagnostic starts with this header. |
| `sz fallback` | The site. One of `sz fallback`, `szr fallback`, `szv catalog`. |
| `12:9` | Line and column of the expression, 1-based. |
| reason | *What* could not be read — the expression shape. |
| `Suggestion:` | The way out, chosen by the expression shape. |

## The two classes of build warning

This is the single most useful distinction in this page.

| Class | Means | Dev build | Production build | `quiet: 'nudges'` | `quiet: true` |
| --- | --- | --- | --- | --- | --- |
| **missing output** | Classes never reached the safelist, so no build step was told to generate their CSS — or a key or value the compiler read emitted a class that styles nothing. The markup names utilities that do not exist. | prints | **prints** | prints | silent |
| **usage nudge** | The classes *were* collected. The message is advice for whoever writes csszyx code. | prints | silent | silent | silent |

The two classes are the default levels of
[`csszyx.config`](/docs/reference/config/#csszyxconfig): missing output is
`error` (or `warn`), a usage nudge is `info`. Setting a level moves a finding
between them — see [Levels in a build](#levels-in-a-build).

<Aside type="caution" title="`quiet: true` hides missing output too">
`quiet: 'nudges'` mutes exactly the set a production build already mutes, and
keeps every report that the build produced less than you asked for. `true` is
blunt: it also hides the missing-output reports. Reach for it only once you
have decided the missing CSS is acceptable.
</Aside>

A separate group of build messages goes straight to `console.warn` and is
**not** gated by `quiet` at all — parser fallbacks, prescan skips, mangle
reports, and the native-binary notice. Each is marked in its table below.

## Every silencing switch

| Switch | Silences | Where |
| --- | --- | --- |
| `quiet: 'nudges'` | Usage nudges, keeps missing-output reports | Plugin option |
| `quiet: true` | All plugin warnings (errors still throw) | Plugin option |
| `diagnostics.rules: { '<id>': 'off' }` | One kind of finding, on every lane and in `csszyx check` | `csszyx.config` (`.ts`, `.mts`, `.js` or `.mjs`) |
| `contentScopeCheck: false` | The unscoped-monorepo warning only | Plugin option |
| `CSSZYX_QUIET_SZ_WARNINGS=1` | The `sz` key/value warnings of the runtime, the rows marked **every mode** included (§ [sz key and value warnings](#sz--key-and-value-warnings)); on the Next Turbopack loader, which takes no `quiet` option, what `quiet: true` mutes (§ [Turbopack](#the-sz-build-diagnostics-under-turbopack)) | Environment |
| `CSSZYX_NO_PROJECT_SCAN_HINT=1` | The one-time `csszyx check` tip | Environment |

See [Plugin Config → Quiet](/docs/reference/config/#quiet-quiet) for the option
itself.

## Levels in a build

Each `sz` build diagnostic carries the id `csszyx check` reports it under —
`unknown-key`, `fallback-nudge`, `ast-budget` and the rest — and its level comes
from [`csszyx.config`](/docs/reference/config/#csszyxconfig) for that id, in
that file. The id decides, not the wording: a reworded message stays where it
was.

| Lane | `off` | `info` | `warn` / `error` |
| --- | --- | --- | --- |
| Vite dev server, development build, webpack `--mode development` | silent | listed with file and line | listed with file and line |
| Production build (Vite, webpack, Rollup, esbuild) | silent | counted in the [closing line](#fallbacks-a-production-build-does-not-list) | listed with file and line |
| Turbopack loader (`next dev` / `next build`) | silent | listed under `next dev`, dropped under `next build` | listed |
| jest transform | silent | dropped | listed |

A build never fails on a level; `csszyx check` is the gate. `quiet: true` mutes
every level. `quiet: 'nudges'` holds `info` back and keeps `warn` and `error`.

The Turbopack loader cannot load the config file, so it reads the levels
`csszyx next prebuild` or `csszyx next watch` resolved into
`.csszyx/diagnostic-policy.json`; without that file it uses the `recommended`
levels. Jest reads the same file, and without it loads the config itself, once
per worker, printing its problems the way a build does. The file lists the
config and every module it imports by a relative path; once one of them changed
since the file was written, jest and the loader both load the config
themselves. A shared preset imported as a package is not listed: run
`csszyx next prebuild` again after updating it. A Vite dev server, every watch build (webpack, `rollup -w`, `vite build --watch`,
an esbuild context) and `csszyx next watch` read the config again when it, or a
module it imports by a relative path, is saved, and print each finding again at
its new level. Run `csszyx next prebuild` again before `next build`.

Jest loads the config the first time a file has something to report, so a fully
cached run never loads it. When a worker cannot read the levels, it says so and
keeps the levels of `.csszyx/diagnostic-policy.json`, or `recommended` without
that file; `{lane}` is `jest` or `the Turbopack loader`:

```text
[csszyx] {lane} could not read the levels {config} sets: {reason}.
  note: this worker reports at the levels in .csszyx/diagnostic-policy.json, or the recommended levels without that file.
```

`{reason}` is `it did not finish loading within 30 s` for a config that never
settles — a server or a timer started at the top level; raise the wait with
`CSSZYX_JEST_CONFIG_TIMEOUT_MS` — or `the config loader printed no result` for
one that ends the process (`process.exit()`) while it loads. A config that
throws is reported with its own error instead.

**Each site prints once.** A dev server compiles a module again when a
stylesheet or another module changes; a finding already printed for that file
is not printed again until the file itself changes — an undo back to an earlier
version counts as a change, so a finding a fix removed and the undo brought
back is printed again. The Turbopack loader is the
exception: Next keeps its warnings per module and drops one a re-run no longer
reports, so the loader reports every run and Next deduplicates.

**At most ten lines per id.** After ten lines of one id in a start or a build —
on a dev server, in one burst of compiles — the rest are counted and one line
closes them:

```text
[csszyx] {id}: +{count} more not listed
  help: `csszyx check --rule {id}` lists every one.
```

The line is headed by the capped id itself, so a search for `[csszyx] unknown-key:`
finds the count beside the ten it lists ([`diagnostics-capped`](https://csszyx.com/e/diagnostics-capped)).

A build prints it at its end; a dev server, the loader and jest print it once
the burst of compiles that produced them has paused for a second, or as the
process exits, whichever comes first. The count is of findings still there: one
an edit fixes or moves before it prints is dropped from it. The next burst
starts a fresh count, so a new finding later in a dev session is listed with
its file and line.

## sz — unresolved expressions

These fire when the compiler cannot read the value you put in `sz={…}`. All
both engine artifacts emit identical wording.

**What each kind means:**

| Kind | Triggered by | Classes still collected? | Fires in production? |
| --- | --- | --- | --- |
| `call` | `sz={makeSz()}` | Yes — `dynamic()` and friends compile correctly | No (nudge) |
| `identifier` | `sz={styles}` where `styles` is not a readable const | Yes, when a caller supplies it | No (nudge) |
| `import` | `sz={imported}` from another module | **No** | **Yes** |
| `member` | `sz={theme.card}` | Yes, when a caller supplies it | No (nudge) |
| `szv-factory` | `sz={myVariants({ … })}` where the compiler saw `myVariants = szv(…)` and refused its config | Yes — the runtime szv path renders | No (nudge) |
| `other` | anything else — a template literal, a conditional | Yes | No (nudge) |
| `variant` | `sz={{ m: 1, hover: x }}` — one variant key whose value only the runtime knows, in an object or an sz array element; a key no table names (`tablet: x` for a project breakpoint) counts as a variant | **No** | **Yes** |

<Aside type="note" title="Why forwarding a prop is only a nudge">
`({ sz }) => <div sz={sz} />` is the documented wrapper pattern — the literal
lives at the *call site*, where it is collected normally. Making that a
production error would fire on working code, so `identifier` and `member` stay
advisory. An **import** is different: the compiler went looking for a
module-level value and could not read it, so nothing collected those classes
anywhere.
</Aside>

**Exact wording** — `{detail}` is the callee name, identifier name, or node
type:

| Kind | Reason | Suggestion |
| --- | --- | --- |
| `call` | ``function call `{detail}()` returns a value unknown at build time`` | ``for static variants, convert it to `szv()`; for runtime data, use `dynamic()`.`` |
| `identifier` | ``identifier `{detail}` could not be resolved to a static value`` | ``make it a module-level or function-body `const` with a literal object value; for variant-based styling use `szv()`, for runtime values `dynamic()`.`` |
| `import` | ``imported binding `{detail}` could not be read at build time`` | ``export it as a `const` with a static object literal; a star re-export, a computed value or `build.importedStaticSz: false` keeps it at runtime; for variant-based styling use `szv()`, for runtime values `dynamic()`.`` |
| `member` | `member expression is not statically resolvable` | ``extract the value to a module-level `const`; for variant-based styling use `szv()`, for runtime values `dynamic()`.`` |
| `szv-factory` | ``szv factory `{detail}()` could not be compiled: its config fails at `{path}` `` | ``make every variant value at that path a static sz object literal with canonical keys and non-overlapping branches; for runtime data use `dynamic()`.`` |
| `other` | ``expression of type `{detail}` cannot be read at build time`` | ``use a literal sz object or a module-level `const`; for variant-based styling use `szv()`, for runtime values `dynamic()`.`` |
| `variant` | ``key `{detail}` holds a value only known at runtime and no sz property claims it, so its classes were never collected`` | ``if the key is a variant, give it a static sz object literal or a two-branch `c ? { … } : { … }`; if it is an sz property, check its spelling; for runtime values use `dynamic()`.`` |

For `variant`, `{detail}` is the key path from the top of the object
(`md.hover`), and the position is the key's. The rest of the object still
compiles: `sz={{ m: 1, hover: x }}` becomes
`className={_szcn("m-1", _szPart({ hover: x }))}`, so `x` is styled at runtime,
but nothing told Tailwind to generate its classes. A three-arm chain, a
conditional with one empty branch, and a namespace import under a variant take
the same path; `c ? { … } : { … }` with two literal branches compiles. When a
css variable or another conditional sits beside the key, the whole object goes
to `_sz(…)` instead, as an unresolvable spread does. A key no sz table claims
takes the same path, since it may be a variant the project declares
(`@custom-variant`, `--breakpoint-*`); a misspelt property key is therefore
reported here too.

When the callee has no readable name — `sz={obj[key]()}` — `{detail}` is `?`.

<Aside type="tip" title="A call to your own szv reads as one, not as a mystery">
`szv-factory` is the `call` kind after the compiler recognises the callee.
Without it, `sz={myVariants({ … })}` reported ``function call `myVariants()`
result is unknown`` and suggested converting to `szv()` — circular advice for
someone already writing one, naming no position. The kind fires only when this
file declared the factory *and* the compiler refused its **config**, so
`{path}` is a real position such as `variants.size.lg.tablet`: go read that
value. A factory whose config qualified, or a call to something the file never
declared, still reports as `call`.

The same substitution happens at `szr(myVariants({ … }))`. One cause, one
message, wherever the call sits.
</Aside>

The `szv catalog` site replaces the suggestion with one of its own:

```text
Pass the config inline, or as a module-level const object literal. A computed or spread config cannot be read at build time, so none of its variant classes are safelisted and they generate no CSS.
```

<Aside type="tip" title="What the import case usually means">
Reading a static object out of another module is on by default, so this
diagnostic normally says the import did not qualify — a star re-export, or a
binding whose value is not a plain object literal. A named re-export through a
barrel is followed and does not report. The other cause is
`build.importedStaticSz` being turned off. See
[Reusing Styles](/docs/reusing-styles/) and
[Plugin Config](/docs/reference/config/).
</Aside>

### Fallbacks a production build does not list

A fallback at an `sz` prop is advisory: the runtime path works and the classes
are still collected, so a production build does not print it. Only the kinds
that mean **absent output** print in every mode: `szr`, `szs`, spreads, budget
bails, and a key or value that emits a dead class.

That makes the fallbacks a production log *does* list a lower bound, never a
total. So the build closes with a count of what it held back — every `info`
finding, not only the fallbacks. That includes a finding your config lowered to
`info`, such as `dead-class`, whose styles are missing, so read the count as
"not listed", not as "handled":

```text
[csszyx] diagnostics-held:
  This build held back {count} finding(s) at `info` and listed none of them.
  help: run a development build to see each one with its file and position.
  note: they are the advisories csszyx handled — a fallback at an sz prop, a className whose precedence over sz is unstated, or a variable hoist the planner declined — and any finding `csszyx.config` sets to `info`.
  docs: https://csszyx.com/e/diagnostics-held
```

Run a development build to see each one with its file and position. In CI, run
[`csszyx check`](#running-it-in-ci) instead: it lists every finding with its file
and line whatever the build mode, and fails the job on the ones at `error`, or
at the level `--fail-on` names. Silenced by
`quiet: true` (blunt mode) along with everything else; `quiet: 'nudges'` keeps
it, because one line saying how much was left out is what stops a calm log from
reading as a clean one.

<Aside type="caution" title="Counting affected sites from a build log">
Because the list is partial, counting how many places fall back by reading the
log undercounts — a component that only ever falls back at an `sz` prop never
appears in it. Read sources when you need the real number.
</Aside>

## sz — key and value warnings

These come from the shared lowering core, so the **same message** appears
whether the value was lowered at build time or by the runtime.

Each line is headed by its code, and the rows below quote the runtime's form:
with no location, the sentence follows the code on the first line. A build
engine that knew the location names it after the code, as the engine's own
messages do, and puts the sentence on the next line.
In production the runtime prints the code, its args as JSON and the code's page
instead of the sentence: `[csszyx] removed-key: {"form":"removed","key":"maskFrom"} https://csszyx.com/e/removed-key`.

<Aside type="caution" title="Most of these are terminal-only">
The main gate is: development **and** not a browser. That means they appear in
your dev-server terminal (build and SSR), not in the browser console. Set
`CSSZYX_QUIET_SZ_WARNINGS=1` to mute them, or run `npx @csszyx/cli check` for a
whole-project pass. The rows marked **browser too** use only the `NODE_ENV`
half of that gate and do reach the console. The rows marked **every mode** say
a class was not emitted at all, so the runtime prints them in production (as the
code and its args) and in the browser too, once each;
`CSSZYX_QUIET_SZ_WARNINGS=1` still mutes them. Every
row below says a class is dead, so the bundler plugin prints the whole family in
a production build as well as a development one; only `quiet: true`, or the
id set to `off` in `csszyx.config`, silences the build's copy.
</Aside>

### Conditional objects

Key and value diagnostics also inspect statically resolved conditional branches,
including ternary spreads, whole-object ternaries, a ternary on one key
(`touch: m ? 'pan-x' : 'auto'`, checked for a known key only) and resolved items
in an sz array. A property shared by both branches is reported once at its source location;
two separate declarations are still reported separately. Both branches are checked
because either may be used. The diagnostics do not change the emitted classes.

An unresolved spread reports `unresolvable-spread` in place of the fallback
nudge, since both name the same site. That warning is not a
certificate that the literal keys beside it are valid: complete key/value checking
of unresolved objects is not supported yet.

When a key warning has no source location, csszyx names the object and the
caller in its place, after the code, so you can find it:


```text

```

And once per process, after the first one, a pointer at the whole-project scan:

```text
[csszyx] dev-warnings-partial: The `sz` key warning above has no source location, so it does not name the file that triggered it.
  help: run `npx @csszyx/cli check` to list every file and key at once; set `CSSZYX_NO_PROJECT_SCAN_HINT=1` to hide this line.
```

Unknown custom keys and removed keys deliberately have different outcomes. A
brand-new key can still target a project-defined Tailwind `@utility`, so csszyx
emits its kebab-case class after warning. A key listed as an alias or removed
migration is not a custom escape hatch: csszyx warns and drops it instead of
silently preserving obsolete API spellings or leaving dead classes in the DOM.

The unknown-key and canonical-key reports print once per message per process,
so server-side rendering does not repeat them on every request. After 512
distinct keys they stop, once, with:

```text
[csszyx] diagnostics-capped: This process has reported {count} distinct unknown sz keys, so further ones are suppressed.
  help: look above for one key repeating with different names; sz keys built from data are the usual cause.
```

An object whose keys come from data — one per record — would otherwise make
every render a new report. The keys printed above the line name the object to
look at. Production is unaffected.

#### Closed keys name a value outside their set

`display`, `position` and `visibility` carry their value as the bare Tailwind
utility — `{ display: 'flex' }` is `flex`, not `display-flex`.
That makes an unrecognised value worse than a dead class: it ships verbatim as
a single unprefixed class name, which is the shape a project's own component
CSS is made of, so `{ display: 'bogus' }` can match a `.bogus` rule that was
never meant for it.

`isolation` and the grouped keys (`nums`, `numFigure`, `numSpacing`,
`numFraction`, `touch`, `touchPanX`, `touchPanY`, `contain`, `containSize`) keep
their utility's fixed part on a typo instead:
`{ numSpacing: 'tabulr' }` emits `tabulr-nums`, which cannot land on a class
name of your own.

CSS closes every one of these value sets, so csszyx names a value outside them,
with the class it emitted and the legal set:

```tsx
<div sz={{ display: 'flex' }} />   // ✅ flex
<div sz={{ display: 'none' }} />   // ✅ hidden
<div sz={{ display: 'flex!' }} />  // ✅ flex! — the important modifier is a class suffix
<div sz={{ display: 'bogus' }} />  // ⚠️ bogus, warned with the legal set
```

The class is still emitted, on purpose. The diagnostic comes from a static
pass that does not look inside a parametric variant such as
`data: { open: … }`; had the build dropped the class instead, a typo there
would vanish with no line to find it by. Emitting keeps the worst case where it
always was — a bare class in the DOM — and the diagnostic covers the rest.

Anything CSS spells but Tailwind does not is still reachable through the escape
hatch: `css: { display: 'ruby' }`.

#### One key per group

`font-variant-numeric`, `touch-action` and `contain` take one key per group of
their CSS grammar (`numSpacing`, `touchPanX`, `containPaint`, …) and one key for
the keywords that stand alone (`nums`, `touch`, `contain`). In one object the
later key wins: the stand-alone key resets the group keys written before it,
and the group keys written after it replace it. Across the layers of an sz array
or an `szv` selection the later layer wins the same way.

A stand-alone key written before a group key of its family is therefore dead,
and csszyx names it. Written by hand it is a leftover; it is also exactly the
shape a spread override leaves, because a spread keeps the overridden key at
the place the spread gave it:

```tsx
const base = { contain: 'strict', containPaint: true };
<div sz={{ ...base, contain: 'none' }} />   // ⚠️ contain-paint: { contain: 'none', containPaint: true }
<div sz={[base, { contain: 'none' }]} />    // ✅ contain-none: the later layer wins
```

A runtime value on one side of a family beside the other side cannot be
settled by the object's order at build time: the build emits both classes, and
Tailwind's stylesheet puts the stand-alone class last whatever the object
says. The build names it; write the two sides as layers instead:

```tsx
<div sz={{ touch: 'none', touchPanX: pan ? 'x' : undefined }} />    // ⚠️ named at build
<div sz={[{ touch: 'none' }, pan && { touchPanX: 'x' }]} />          // ✅ later wins
```

A stand-alone key holding a value of one of its groups (`contain: 'paint'`)
emits that group's class, but as a stand-alone value it resets the group keys
written before it, so csszyx names the group key to write instead.

#### An object under `--*` or `container` is not a variant

Any key holding an object becomes a class prefix, which is how a project's own
`@custom-variant` and its `--breakpoint-*` names work without csszyx knowing
them. csszyx therefore cannot tell a typo'd breakpoint from one your CSS
declares, and does not guess.

Two keys are decidable, because csszyx defines what they mean and neither
meaning is a variant:

```tsx
<div sz={{ '--v-x': '0.18' }} />          // ✅ [--v-x:0.18]
<div sz={{ '--v-x': { p: 4 } }} />        // ❌ --v-x:p-4 — warned
<div sz={{ container: true }} />          // ✅ container
<div sz={{ container: { sm: { p: 4 } } }} />  // ❌ container:sm:p-4 — warned
```

For a container query, the key is the query itself: `{ '@sm': { p: 4 } }` emits
`@sm:p-4`.

#### Border styles are set for every side, not per side

CSS gives each side its own `border-style`; Tailwind spells the style at the
root only. `borderStyle` is the key for it, and the side keys take a width:

```tsx
<div sz={{ borderStyle: 'none' }} />  // ✅ border-none — every side
<div sz={{ borderB: 2 }} />           // ✅ border-b-2 — this side's width
<div sz={{ borderB: 0 }} />           // ✅ border-b-0 — this side, no border
<div sz={{ borderB: 'none' }} />      // ❌ dropped: border-b-none has no rule
```

`border-b-none` reached the safelist, Tailwind generated nothing for it, and the
border stayed. All six style keywords behave this way on all ten side keys — the
four physical sides, the two axes, and the four logical ones. Widths, colours and
theme tokens are unaffected on every one of them.

#### Keys that need a build-time value

A runtime value normally compiles to `<prefix>-(--_sz-<key>)` plus a `style`
custom property. That works whenever the var form is the same utility as the
literal form with the value deferred — which is most of the sz vocabulary, but
not all of it.

```tsx
<div sz={{ color: tone }} />       // ✅ text-(--_sz-color) — a colour utility
<div sz={{ textAlign: align }} />  // ❌ dropped: text-(--v) is a COLOUR, not an alignment
<div sz={{ display: how }} />      // ❌ dropped: display-(--v) is not a utility at all
```

`color` and `textAlign` share the `text-` prefix and only one of them has a var
form, so this is per **key**, never per prefix. Both failures used to be silent:
the first wrote `color: var(…)` holding something like `"center"`, an invalid
value that also unsets the inherited colour; the second put a class in the
safelist that Tailwind generated no rule for.

##### What you get now

```tsx
<div sz={{ p: 4, textAlign }} />
// → <div className="p-4" />
```

```text
[csszyx] runtime-value: `{key}` cannot take a runtime value: Tailwind has no utility for this key that reads a CSS variable.
```

The sibling keys survive — only the one property is dropped, and the `style`
attribute is not emitted at all.

##### Write it one of these three ways

**One or two options — a ternary between literals.** Nothing else needed; this
is fully build-time.

```tsx
<div sz={{ p: 4, textAlign: centered ? 'center' : 'left' }} />
// → className={`p-4 ${centered ? "text-center" : "text-left"}`}
```

**A real set of options — name them with [`szv`](/docs/szv/).** Read the factory
through [`szr`](/docs/reusing-styles/) on `className`: that is the position the
compiler resolves at build time.

```tsx
const alignSz = szv({
    base: { p: 4 },
    variants: {
        align: {
            left: { textAlign: 'left' },
            center: { textAlign: 'center' },
            right: { textAlign: 'right' },
        },
    },
});

<div className={szr(alignSz({ align: side }))} />
// → className="p-4 text-left" | "p-4 text-center" | "p-4 text-right"
// all three safelisted, no runtime helper
```

<Aside type="caution" title="`sz={alignSz({…})}` also works, but not at build time">
Passing the factory result straight to `sz=` produces the right CSS — the
classes are still safelisted — but the class *selection* runs through `_sz()` on
every render, and the build reports a fallback whose advice ("convert to
`szv()`") is already taken. Use `className={szr(…)}` until that is fixed.
</Aside>

**An open-ended value from data — [`dynamic()`](/docs/dynamic/).** Only when the
value genuinely is not one of a known set; it injects CSS in the browser.

### Colors

A colour key takes its opacity in the object form, so a string with a slash
opacity (`bg: 'red-500/50'`) emits nothing on every lane. The build reports it
with the kind `slash-opacity-string` (an `error` under `recommended`), and the
runtime prints the same text once per value, in the browser and in production
too, because the class is missing. A trailing `!` is left out of the value it
names.

The object form is the one spelling for an opacity. A plain slash opacity
inside it (`bg: { color: 'red-500/50' }`) is still written as the class, and the
build reports it with the kind `color-slash-opacity` (an `error` under
`recommended`) so the opacity moves to `op`. When both are given, `op` is the
opacity: `{ color: 'red-500/50', op: 20 }` writes `bg-red-500/20`. A trailing
`!` ends the class (`bg-red-500/20!`). Anything else after the slash
(`red-500/50/30`) is written as given and judged at build.

Any other colour string is written as given, on every lane: `bg: 'white/50'`
is `bg-white/50`, `bg: '50%'` is `bg-[50%]`. Whether the project's Tailwind
serves the class is its answer at build, where the dead-class check reports a
class that produces no CSS; the runtime does not judge it.

and the theme group registry — which `classify` reads — says so once.

| Message |

The `registerSzcnGroups` message is printed once, in development, on the first
hand-written call to `registerSzcnGroups`. On 0.17 that call was how a class
written in plain CSS joined a merge group. Every group it took is a `@theme`
namespace, so the migration is to declare those tokens under `@theme` and
delete the rules you wrote for the classes, with an integration that supplies
the merge table. A class your own CSS selects on stays out of every merge, and
so does one from `@utility`, a plugin or plain CSS. Without that table, `szcn` removes only
exact repeats.

The fix in the three theme-token cases is renaming the token in your `@theme` block. With
`--color-balance` declared, `szcn('text-red-500', 'text-balance')` is
`'text-balance'` — that class now sets `color` too — while
`szcn('text-balance', 'text-red-500')` keeps both, because the colour class does
not cover `text-wrap`.

### A class name with more than one author

Tailwind v4 treats a class name as a namespace several sources contribute to,
and when two of them land on the same name it **merges** the declarations and
says nothing. csszyx reports the declaration site, because that is the one
place someone can change:

```text
[csszyx] "@utility {name}" collides — {reason}. Tailwind merges both declarations into one rule and reports nothing, so the class carries styles no single place in your CSS shows. Every use is affected, including sz props that spell it correctly. Rename it; if a multi-property class is the point, declare it under a name nothing else claims.
```

`{reason}` is either `declared twice` — two `@utility` blocks claiming one name
— or `a theme token already generates it`, where a `@utility` takes a name a
`--color-*` token already produces under one of its prefixes.

There is deliberately no ignore comment. A class that is meant to set several
properties has a spelling that costs nothing: a name nobody else claims. An
ignore would silence a warning about damage that lands in other files.

## Build pipeline

Everything that decides **which files** get compiled and **whether the CSS gets
generated**.

### The safelist moved

The safelist csszyx writes for Tailwind lives at `.csszyx/csszyx-classes.txt`.
Every producer performs the move and says what it did; these messages come from
the Vite, Rollup and webpack plugins, from `csszyx next prebuild` and
`csszyx next watch`, from the Next Turbopack loader, and from the PostCSS plugin.

```text
[csszyx] removed {file}: the safelist now lives at {safelist}. Update any hand-written @source that named the old file, or drop it and list '@csszyx/unplugin/postcss' before '@tailwindcss/postcss' in postcss.config.
```

Printed once per removed file (`{file}` is `csszyx-classes.html` or
`.csszyx/next-loader-classes.html`; `{safelist}` is `.csszyx/csszyx-classes.txt`).
Only a file csszyx itself wrote is removed; a file you keep at the old name
stays. Nothing to do unless a stylesheet still names the old file, which the
next message catches.

```text
[csszyx] could not remove {file}: {reason}. Delete it by hand.
```

The new safelist is already written by then; delete the leftover yourself.

```text
[csszyx] {stylesheet}: @source "{target}" names the old safelist, which csszyx no longer writes. The safelist is now {safelist}, and csszyx adds the directive itself: remove this line. Vite, Rollup and webpack inject it; on Next.js list '@csszyx/unplugin/postcss' before '@tailwindcss/postcss' in postcss.config.
```

A build **error**, not a warning, and it is not gated: a stylesheet pointing at
a file that is gone would scan nothing and lose every csszyx class in silence,
so the build stops instead. Remove the line.

```text
[csszyx] {config} does not list '@csszyx/unplugin/postcss'. Next.js reads the safelist only through that plugin: list it before '@tailwindcss/postcss', or no sz class gets CSS.
```

Printed by `csszyx next prebuild` and `csszyx next watch`. Add the plugin line.

```text
[csszyx] '@csszyx/unplugin/postcss' is listed after '@tailwindcss/postcss'. Tailwind has already compiled the stylesheet by then, so the safelist is never read: list '@csszyx/unplugin/postcss' before '@tailwindcss/postcss'.
```

A PostCSS **error**: reorder the two plugins.

### The safelist could not be written

```text
[csszyx] could not write the generated safelist to {path}: {reason}. Tailwind scans that file for the classes csszyx found, so the CSS it generates will be missing them. Check that the directory exists and is writable.
```

The build carries on without those classes, so the page renders with `sz` props
that produce no CSS. Said once per path — a dev server retries the write on
every edit. A read-only `.csszyx`, a full disk, or a path owned by another user
all arrive here.

### Tailwind entries set different prefixes

```text
[csszyx] your Tailwind entries set different prefixes, so no class name csszyx emits can be served by all of them:
  {file}   {prefix(name) or no prefix}
  help: give every entry the same `@import "tailwindcss"` line, or list the stylesheets this build loads in the csszyx `tailwindStylesheet` option.
  note: the build stopped before transforming any module; nothing was written.
```

A build **error**, one line per stylesheet. csszyx writes one prefix before every
class, so with two prefixes in play part of the app would get classes that style
nothing. A stylesheet another entry imports has no say of its own, and entries
that differ only in `important` do not stop the build. Usually one of the listed
files is a fixture or an old copy: name the real one in the `tailwindStylesheet`
option ([configuration](/docs/reference/config/)). `csszyx next prebuild` and
`csszyx next watch` print the same messages naming the `--tailwind-stylesheet`
flag in place of the option, and the Turbopack loader takes the list as
`csszyxTurbopack({ tailwindStylesheet })`. When the other entry belongs to
another app under the same root, `--ignore <patterns>` on those two commands
leaves its directory out for the loader too, and the Jest transformer takes the
same patterns in its `ignore` option.

```text
[csszyx] the ignore pattern `{pattern}` is negated, and an ignore list cannot take one: each pattern only adds paths to leave out.
  help: narrow the pattern that covers too much, so that nothing has to be taken back out.
```

An **error** from `csszyx next prebuild`, `csszyx next watch` and the Jest
transformer's `ignore` option. Each pattern is matched on its own, so `!legacy/keep.css` would not take one file
back out of `legacy/**`: it would match every path except that file, the app's
real Tailwind entry included.

```text
[csszyx] the csszyx `tailwindStylesheet` option lists stylesheets that are not there: {paths} (relative to {rootDir}).
  help: list the stylesheet that imports Tailwind for this build, relative to the project root.
```

A build **error**. A mistyped path would otherwise leave nothing to read the
prefix from. Fix the path.

```text
[csszyx] stylesheets that reach Tailwind did not compile, so csszyx cannot read the prefix its classes need:
  {file}: {reason}
  help: fix the stylesheet; if this build does not load it, list the stylesheets it does load in the csszyx `tailwindStylesheet` option.
  note: no module was transformed; without the prefix every emitted class could style nothing.
```

A build **error**. The stylesheet imports Tailwind, directly or through another
stylesheet, and something it imports could not be loaded, so the prefix it sets
is unknown. `{reason}` is the first line of what the compile reported, usually a
path that does not resolve. Fix the import. If the file is a leftover the app no
longer loads, name the stylesheets it does load in `tailwindStylesheet`.

```text
[csszyx] these stylesheets did not compile and never reached Tailwind, so csszyx read the prefix without them:
  {file}: {reason}
  help: if the app loads one of them, fix its import; otherwise list the stylesheets the app loads in the csszyx `tailwindStylesheet` option.
```

A warning; the build carries on. A stylesheet that never reaches Tailwind cannot
set a prefix, so it does not change what csszyx emits. It is listed because a
broken import in a file the app does load is still worth fixing.

```text
[csszyx] {file} imports `{specifier}`, which this build's Tailwind cannot resolve, so csszyx left the stylesheet out of the prefix and the merge model.
  help: a build that loads one of them stops on that import; import the file by a relative path (only a Vite build follows an alias, through `resolve.alias`). If the build does not load it, list the stylesheets it does load in the csszyx `tailwindStylesheet` option.
```

A warning, printed in production too and muted only by `quiet: true`, as every
warning about the build's environment is; once per process for each stylesheet
and import, and the build carries on. The import names neither
a relative nor an absolute path (an alias such as `@/styles/theme.css`, or a
package), and the resolver of this build's Tailwind finds no stylesheet for it.
`@tailwindcss/postcss`, which Next.js, webpack, Turbopack, Rollup and esbuild
builds run, reads such a target as a package and follows no alias and no
tsconfig `paths`. A Vite build follows `resolve.alias`, and tsconfig `paths`
only with `resolve.tsconfigPaths` and `@tailwindcss/vite`. If the app loads the
stylesheet, Tailwind stops the build on that import by itself. If it does not
(a leftover copy, a stylesheet of another app), the build is fine, and csszyx
reads no prefix and no theme from that file. `csszyx next prebuild` and
`csszyx next watch` print the line naming the `--tailwind-stylesheet` flag;
they take no `quiet` option, so they always print it.

```text
[csszyx] your Tailwind entry sets important, which csszyx does not emit for yet: every utility is `!important`, so a class csszyx emits cannot override one the project already applies.
  help: drop important from the `@import "tailwindcss"` line, or keep it and style those elements with `className` until csszyx supports it.
```

A warning that fires in production. The build carries on, but an `sz` override
loses to the class it was meant to override.

```text
[csszyx] csszyx merges no class in this build: {file} did not compile with its `@utility` blocks and plugin classes taken out ({reason}).
  help: report it at https://github.com/nguyennhutien/csszyx/issues with the plugin or `@utility` block the stylesheet uses.
  note: every class is kept: `{ pb: 2, p: 4 }` emits `pb-2 p-4`, a `className` class stays next to the `sz` classes, and `szcn` removes only exact repeats.
```

A warning that fires in production, printed once each time the build reads the
stylesheets, and by `csszyx next prebuild` and `next watch`. Only Tailwind's own
utilities merge, so csszyx compiles the stylesheet a second time with its
`@utility` blocks removed and its plugins registering no class. When that
compile fails, csszyx cannot tell which classes are Tailwind's, so it merges
none: output is what concatenating the classes gives, and the stylesheet order
decides between them.

### The Tailwind prefix changed during a session

```text
[csszyx] {file} changed the Tailwind prefix from {before} to {after}: recompiled every module and reloaded the page.
```

Printed by a Vite dev server, once per change, whatever `quiet` says. Every
module compiled before the edit carried classes under the old prefix, so the
server lowered every source again and reloaded the page. `{before}` and
`{after}` read `no prefix` when none is set. Nothing to do.

```text
[csszyx] {file} changed which sz keys cover each other: recompiled every module and reloaded the page.
```

The same reload for a stylesheet edit that changed which class a later `sz`
key covers — a `@theme` token added or removed, a rule of your own that starts
or stops selecting on a Tailwind class. Each
module merged its static `sz` objects under the stylesheet it was compiled
with, so the server compiled every module again. Nothing to do.

```text
[csszyx] {n} class(es) in {m} file(s) were removed: another class on the same element sets every property they set.
  help: `csszyx check --rule merge-covered-key --rule merge-covered-class` lists them.
  note: set `merge-covered-key` and `merge-covered-class` to `'off'` in `diagnostics.rules` of `{config}` to hide this line; `build.mergeCoveredClasses: false` keeps the classes.
```

`{config}` is the project's config file, or the name `csszyx init` would give
it when there is none.

The `info` rendering of `merge-covered-key` and `merge-covered-class`, the
default under the `recommended` preset. Printed once when a Vite dev server or
a webpack development build starts, and again when an edit to the config during
that session (on a webpack watch, at the next rebuild) gives either id another
level; never in production, and never on Rollup, esbuild, jest or Turbopack. Each class was dropped on purpose: a later key in
the same `sz` object (`merge-covered-key`), or an `sz` class beside a static
`className` (`merge-covered-class`), sets every property it sets. The line
names only the ids still at `info`. If you needed one, the audit shows where it
was; move it into `sz` after the key that covers it, or set
`build.mergeCoveredClasses: false` to keep every class. Setting both ids to
`off` hides the line and changes nothing else.

```text
[csszyx] {file}:{line}: `{key}` (`{class}`) removed: a later key in the same `sz` object sets every property it sets. (merge-covered-key)
[csszyx] {file}:{line}: `{class}` removed from `className`: an `sz` class on the same element sets every property it sets. (merge-covered-class)
```

The same finding at `warn` or `error` — the `atomic` preset, or a level set in
`diagnostics.rules`: one line per removed class with its file, line and key,
printed when the dev server or build starts, in production too, and again when
a config edit during a dev server or a webpack watch changes the level.

```text
[csszyx] {files} changed the Tailwind prefix from {before} to {after}, but this watch session compiled its modules under the old one, so their classes would style nothing.
  help: stop the watch and start it again.
  note: modules keep the classes they were compiled with until the restart.
```

A watch **rebuild error** on webpack, `rollup -w`, `vite build --watch`, an
esbuild context and rspack. Those bundlers keep the modules they already
compiled and a plugin cannot make them compile everything again, so every
rebuild fails with this until the prefix is back or the watch restarts.

```text
  note: {session} keeps the prefix it last read ({prefix}) until the stylesheets agree again.
```

Closes a [prefix disagreement](#tailwind-entries-set-different-prefixes) or a
stylesheet that did not compile when either happens during a Vite dev server
(`the dev server`) or a watch rebuild (`this watch session`). It is a warning
there, not an error: the author is mid-edit, and the next save usually fixes it.

```text
  note: `csszyx next watch` keeps watching; the loader stops on this error until the stylesheets agree again.
```

Closes the same two messages when `csszyx next watch` reads them after a
stylesheet edit. The watch goes on, but the stylesheet facts it records are not
rewritten, so the Turbopack loader stops on the same error until the edit is
fixed.

```text
[csszyx] internal error: the build asked for the project's Tailwind prefix before it read the project's stylesheets. This is a csszyx bug; please report it with the bundler you build with.
```

A build **error** that should never reach you: a bundler lane reached the
engine without reading the stylesheets first. Report it with the bundler and
its version.

### A stylesheet edit changed which sz keys cover each other

```text
[csszyx] {files} changed which sz keys cover each other, but this watch session merged its modules under the old stylesheet, so an sz object may keep a class a later key now covers, or leave out one it no longer covers.
  help: stop the watch and start it again.
  note: this rebuild finished; only the objects whose keys changed cover are stale until then.
```

A later key in a static `sz` object replaces an earlier one whose CSS it
covers, and the build works that out from your stylesheet when it compiles the
module. A watch rebuild on webpack, `rollup -w`, `vite build --watch`, an
esbuild context or rspack keeps the modules it already compiled, so after an
edit such as removing a `@theme` token those modules still carry the old
answer. The rebuild goes on, since only the objects whose keys changed are
affected; restart the watch to compile them again. A Vite dev server needs no
restart: it compiles every module again and reloads the page.

### A rule selects on a class the build already removed

```text
[csszyx] `{class}` was removed from {file} before csszyx read a rule that selects on it, so the page would lose it.
  help: set `build.mergeCoveredClasses: false` to keep every class, or restart a watch session.
  note: csszyx reads every source for such rules before it merges; this one came later, from a module outside the project walk or an edit during a watch.
```

A build **error**. A merge never removes a class that a rule selects on: a
rule in a stylesheet, a component's `<style>` block, or an arbitrary variant
such as `group-[.shadow-md]:p-2`, written in markup or lowered from an `sz` key.
The build reads all of them before its first merge. This stops the build
when it meets one only afterwards, from a module outside the directories it
walks or from an edit during a watch, because the class is already gone from
`{file}`. A Vite dev server does not stop: it compiles every module again and
reloads the page.

### Next.js with Turbopack

Turbopack compiles each module on its own, so csszyx cannot hold the class set
in memory the way it does on the Vite lane. Everything below is a build **stop**
rather than a warning: carrying on would ship a page whose classes have no CSS.

```text
[csszyx] Next Turbopack production cache is not ready for {root}: {reason}. Production builds with Turbopack need the csszyx safelist seeded first: npx csszyx next prebuild 'app/**/*.tsx'. Wire it into package.json so plain builds keep working: "build": "csszyx next prebuild 'app/**/*.tsx' && next build". Docs: https://csszyx.com/docs/installation#nextjs-turbopack-setup
```

Printed across several lines in the terminal. Run the prebuild once, then keep
the `build` script the message names so the next `next build` finds the cache
already seeded.

```text
[csszyx] Next Turbopack does not support production CSS variable mangling for {file}. Use Next Webpack mode for full csszyx parity.
```

```text
[csszyx] Next prebuild does not support production CSS variable mangling. Use Next Webpack mode for full csszyx parity.
```

Mangling rewrites variable names across the whole bundle, which needs a view of
every module at once. Turbopack does not offer one; the Webpack lane does.

```text
[csszyx] Next source transform failed closed for {file}: source still contains csszyx sz syntax.
```

The transform ran and left `sz` behind, which would reach the browser as an
unknown prop. Stopping is the safe answer, and the file is named because the
input that produced it is worth seeing.

```text
[csszyx] Next safelist watcher failed to run its initial cycle.
```

The watcher could not complete its first pass, so nothing after it can trust the
safelist. Usually a permissions or path problem under `.csszyx`.

```text
[csszyx] next watch is waiting for the safelist lock held by the Turbopack loader (process {pid}). Classes added meanwhile get no CSS until it is released; a lock left by a loader that exited is recovered within 30 s.
```

Unlike the stops above, this one is a notice: the watcher keeps running. `next
watch` and the Turbopack loader share one lock, and the loader holds it for about
a millisecond at a time, so an overlap normally clears on the next retry without
a word. This prints once when the wait passes a second, which in practice means
the loader was killed while holding the lock. The wait ends on its own when that
lock goes stale. If it lasts more than a minute, the watcher stops and reports the
lock instead.

A shard another csszyx version wrote is left out of the safelist, and said:

| Message | Kind |
| --- | --- |
| `[csszyx] {shard} is a safelist shard in format {n}, and this version reads format {m}: its classes are left out of the safelist.` + ``help: run `csszyx next prebuild` with the csszyx this project installs, which writes every shard again.`` | Warning, once per shard, from the loader, `csszyx next prebuild` and `csszyx next watch`. |

Each source's classes sit in a shard under
`.csszyx/cache/safelist-shards/`, and this one was written by a csszyx whose
shards this one cannot read: two versions ran against the same project, such as
a global `csszyx` beside the one in `node_modules`. The shard is left on disk
for the session that wrote it, and its classes get no CSS from this one until
the prebuild of the installed version writes the shard again. A field a newer
version adds to a shard does not change its format, so this only follows a
change an older reader cannot read past.

#### The `sz` build diagnostics under Turbopack

The Turbopack loader prints the same `sz` build diagnostics as the Vite and
webpack lanes, at the same [levels](#levels-in-a-build): `warn` and `error` in
every mode, `info` only under `next dev`. It reads the levels from
`.csszyx/diagnostic-policy.json`, which `csszyx next prebuild` and
`csszyx next watch` write from `csszyx.config`. They arrive as Turbopack warnings on the
module, so Next prints them under the file's path in the terminal, shows them in
the dev overlay, and drops them once the module compiles clean. A production
build lists none of the advisories and, unlike the other lanes, prints no count
of them, because a loader never sees the build end; run
[`csszyx check`](#running-it-in-ci) for the full list.

The loader takes no `quiet` option. `CSSZYX_QUIET_SZ_WARNINGS=1` in the
environment of `next dev` or `next build` mutes what `quiet: true` mutes on the
other lanes.

### The Tailwind prefix on the Next.js lanes

```text
[csszyx] {lane} has not read the Tailwind prefix for {root}: {reason}.
  help: run `csszyx next prebuild` before `next build`, and `csszyx next watch` beside `next dev`; both read the stylesheets first.
  note: without the prefix every class this lane emits could style nothing.
```

A build **error** from the Turbopack loader or `csszyx next prebuild`. Those
lanes read the prefix from `.csszyx/cache/stylesheet-facts.json`, and it was
missing, or a stylesheet changed after it was written. Run the command the help
line names. A `next dev` loader with no watcher reads the stylesheets itself
instead of stopping.

```text
[csszyx] internal error: a Next lane asked the engine to lower a module before it read the project's Tailwind prefix. This is a csszyx bug; please report it with the Next.js version you build with.
```

Should never reach you. Report it with the Next.js version.

### An sz class produces no CSS

```text
[csszyx] {file}:{line}:{column}: `{class}` (sz key `{key}`) is emitted by an sz prop and produces no CSS under this project's Tailwind (dead-class).
  help: fix the sz key or value, or define the class with Tailwind's @utility; `csszyx check --rule dead-class` lists every one.
```

The build-time `dead-class` finding, the same id and the same answer as
[`csszyx check`](#cli). `{ break: 'bogus' }` lowers to `break-bogus` and
`{ justify: 'safe-center' }` to `justify-safe-center`: both keys are real, so
no key warning fires, and the class sits in the DOM styling nothing. The build
already compiles the project's Tailwind to settle the merge table, and asks it
about every class an `sz` prop emitted; `{file}` is the first file, in path
order, that emits the class and whose level lists it — an `overrides` entry
that turns `dead-class` off for one file, or holds it at `info` in a production
build, moves the line to the next file that emits the class. A class no file
lists is counted once in the production closing line when any file holds it. The line, column and key are where that key is written, on every lane —
Vite, Rollup, webpack, and under Turbopack through `csszyx next prebuild` and
`csszyx next watch` — for a class that is the only one of its object as for one
of several. A class with no recorded site (a value only known at runtime) names
the file alone.

Printed by Vite and Rollup builds (`renderStart`), webpack (`finishModules`),
and under Turbopack by `csszyx next prebuild` and `csszyx next watch`, which
settle the table there (`CSSZYX_QUIET_SZ_WARNINGS=1` mutes them there, as it
mutes the loader). It is `error` under both presets: printed in every mode,
never failing the build — gate on `csszyx check`, which exits 1 on it. Only
classes an `sz` prop emitted are asked about; names written in `className` are
the app's own and are never reported here. A class the project defines on
purpose goes in `diagnostics.allow.classes`; `diagnostics.rules['dead-class']`
set to `off` hides the line.

### `.gitignore` cannot be read

### Monorepo content scope

```text
[csszyx] Tailwind content detection is UNSCOPED in a monorepo. That @source is your package, relative to the CSS file; csszyx auto-injects one for the classes it generates, so only your own templates need listing. Guide: https://csszyx.com/docs/monorepo-content-scope/
```

## Mangling

{/* The hazard messages below are quoted as ONE line each, though the build
prints them as paragraphs. That is deliberate: scripts/validate-warning-docs.mjs
only checks the line carrying the `[csszyx]` prefix, so breaking a message
across lines silently drops its finding and its remedy out of the anti-drift
gate. Keep them on one line. */}

Mangling replaces class names with short tokens. It is an **obfuscation**
feature — see [Plugin Config](/docs/reference/config/#production). Two
reports exist, both ungated.

### Hybrid hazards

Printed when mangled tokens collide with class names in CSS csszyx does not
own, or when a mangled class has no emitted rule:

```text
[csszyx] production mangle found hybrid hazards: {n} mangled token(s) collide with class names in non-csszyx CSS (e.g. …) — those tokens will cross-contaminate external ".{token}" elements. HOTFIX: pass `production: { mangle: false }` to the csszyx plugin to ship now. THEN fix it: if these short names are in your OWN CSS, rename them to something specific (e.g. `.x` → `.resize-handle-x`) — short/common names also clash on specificity with other libraries. Only for names in a third-party stylesheet you cannot edit, list them in `production.mangleExclude` instead. Run `npx @csszyx/cli scan-collisions` to find every offending name.
```

The orphan clause reads `{n} mangled class(es) have no emitted CSS rule (e.g.
…) — those elements lose styling.` and, when there are no collisions, closes
with a different remedy pointing at the CSS pipeline instead.

A stylesheet that matches classes by their text is the third hazard. The clause
names the selector and the classes it was matching, and the remedy is a
paste-ready `production.manglePreserve`:

```text
[csszyx] production mangle found hybrid hazards: {n} attribute selector(s) match class names by text (e.g. …) — those rules stop matching once the classes are renamed, so the elements lose those styles. Keep those classes readable with production.manglePreserve: [{entries}] (paste-ready), or key the rule off a data attribute, which mangling never touches. production.mangleExclude cannot help here: it reserves token names and does not keep a class from being renamed.
```

The sample after `e.g.` is each selector followed by the classes it was
matching, and the paste-ready value is a prefix (`'bg-tag*'`) when every renamed
class starts with the selector's value, the exact names otherwise. When a selector
such as `[class^="y"]` in external CSS would begin matching the tokens
themselves, the clause reads `{n} attribute selector(s) would start matching
mangled tokens instead (e.g. …).` followed by its own remedy: `Reserve those token names with production.mangleExclude: [{tokens}] (paste-ready) so no class is renamed to one of them, or key the rule off a data attribute, which mangling never touches; a prefix or substring selector goes on matching other tokens, so the data attribute is the durable fix.`

### A `manglePreserve` entry matched nothing

```text
[csszyx] production.manglePreserve: {n} {entries} matched no csszyx class in this build ({list}) — nothing was preserved for them. Check the spelling against the class census; an entry keeps a class only when its name is exact, or when it ends in `*` and the class starts with the rest.
```

Printed once per build. A silent no-op here is the defect the option exists to
fix, so the build says which entries did nothing.

### `manglePreserve` rejects an entry

Both **fail** when the plugin is created, before any build runs:

```text
[csszyx] production.manglePreserve[{index}] must be a non-empty string (an exact class name, or a prefix ending in `*`); got {value}.
```

```text
[csszyx] production.manglePreserve must not contain a lone `*`: it would keep every class and silently turn `production.mangle` into a no-op. Name a prefix (`bg-tag-*`) or set `production.mangle: false`.
```

A RegExp is rejected on purpose: a stateful flag makes a match alternate across
the census, a RegExp serialises to `{}` in the config hash, and a pathological
pattern can stall the build for seconds per class.

### A `mangleExclude` name that can never be a token

```text
[csszyx] production.mangleExclude: {n} {names} can never be a mangle token ({list}) — tokens are short base62 strings, so those entries do nothing. To keep a class from being renamed, list it in `production.manglePreserve` instead.
```

Tokens never contain `-`, `_` or `:`, so a class name listed under
`mangleExclude` was almost certainly meant for `manglePreserve`.

### Mangling made the build bigger

```text
[csszyx] production.mangle is making this build BIGGER: +{n} B gzipped. The runtime mangle map costs {n} B via {channels}, while the mangled CSS saves {n} B and the shortened classes in code save {n} B. Mangling is a name-obfuscation feature; over a compressed response it does not reduce payload, because utility class names compress far better than the map they need. If you enabled it for size, set `production.mangle: false`. If you enabled it to hide class names, this is the expected price and you can ignore this. Two copies is not a misconfiguration: the bundle carries the map the runtime reads, and the HTML carries the same census for the hydration checksum.
```

The CSS clause flips to `the mangled CSS COSTS {n} B (short tokens compress
worse than the names they replaced)` when shortening lost.

Also: `[csszyx] mangleVars skipped component CSS variable hoist for {name}
across {n} usages: {reason}` where `reason` is `no-lca`, `non-host-ancestor`,
or `max-depth`. It is a usage nudge: the planner declined an optimisation and
every class and variable is still emitted, so a production build holds the line
back and counts it in the advisory total instead.

### Global variable aliasing

`production.mangleGlobalVars` renames custom properties you list, so csszyx
refuses any token it cannot prove is yours to rename. Every check below
**fails the build** rather than warning — aliasing the wrong property would
silently unstyle whatever else reads it. They arrive together under one error:

```text
[csszyx] production.mangleGlobalVars validation failed:
[{code}] {token} ({file}:{line}:{col}): {message}
```

| Message | Means | Fix |
| --- | --- | --- |
| `Global variable token {name} is not defined in scanned CSS.` | The token was listed but no scanned stylesheet declares it — usually a typo, or a file outside the scanned set | Correct the name, or widen the CSS the plugin scans |
| `Global variable token {name} is reserved and cannot be aliased.` | Tailwind owns the name, or your own `reserved` list claims it | Drop it from `tokens` |
| `Global variable token {name} uses csszyx reserved namespace {prefix}* and cannot be aliased.` | The name collides with the prefix csszyx allocates aliases from | Rename the property in your CSS |
| `Global variable token {name} is declared inside @theme and cannot be aliased.` | Tailwind generates utilities from `@theme` tokens, so renaming one breaks them | Move it out of `@theme`, or drop it from `tokens` |
| `Registered custom property {name} cannot be aliased: @property gives it a type and inheritance behaviour that an alias would not carry.` | `@property` gives the name a type and inheritance behaviour an alias would not carry | Drop it from `tokens` |

### Alias plan mismatch

```text
[csszyx] production.mangleGlobalVars validation failed: CSS alias plan {actual} does not match source-transform alias table {expected}.
```

The names the stylesheet was rewritten with and the names the source transform
recorded have to be the same set. When they are not, some variable would be read
under one name and written under another, so the build stops rather than ship a
page whose custom properties resolve to nothing. Both tables are printed; the
difference between them is the bug.

Every pass marks its findings the way the sz-issue report does. A finding
quieter than `error` is listed with `(info)` or `(warn)` in front of it. While
any finding of the pass is at `--fail-on` or louder its summary starts with
`✖`; when none is, it starts with `!` instead, and every summary with such
findings ends `{k} below --fail-on {level}, which do not fail the run.`

A skip is not always harmless. Two things can stop the dead-class pass, and
only one of them is your project's:

- **Nothing to ask** — no Tailwind installed, or a version with no design
  system. The command skips and **passes**: failing here would break every
  consumer who does not build with Tailwind.
- **The question could not be answered** — a Tailwind entry was found and did
  not compile, so the pass was supposed to run and could not. The command skips
  and **fails**, because a check that never runs is indistinguishable in CI
  from one that found nothing, and a project can otherwise stay green for
  months after its entry stopped compiling.

Several sz keys lower under one Tailwind prefix, so a keyword belonging to one
of them compiles cleanly on another: `color: 'balance'` emits `text-balance`,
which sets `text-wrap` and no colour at all. The type cannot reject it — a
colour may be any theme token — and the class is real, so the dead-class pass
is quiet too. The command reads the CSS property the class actually sets and
compares it with the one the key sets. That comparison separates the mistake from
`fill: 'none'`, where the keyword sets exactly the property `fill` sets.

Your own stylesheet decides. A project that declares `--color-balance` has
given the spelling a meaning, and the report disappears for it.

The pass covers keys whose documented values are theme tokens and nothing else
— the colour keys, `bg`, `fontSize`, `fontFamily` and `fontWeight`. `outline`,
`ring` and `border` are left out: each takes a colour **and** values of its own
(`outline: 'none'`, `border: '3px'`), so a foreign value there cannot be told
from an owned one. `bg` looks like one of them and is not — every other
background domain has its own key, `bgSize` and `bgImg` among them, so
`bg: 'cover'` is reported.

Declaring `--color-balance` does not add a colour class. `text-balance` is
already a static utility, so Tailwind merges the two readings and the class
ends up carrying `text-wrap: balance` **and** the colour — it then competes on
`color` with every other colour class. A colour class written after it does not
cover `text-wrap`, so `szcn` keeps both, and the stylesheet's order decides the
winner instead of the order the arguments were passed.

That is wrong output rather than a missed optimisation, so the command exits
non-zero. `--allow-token <name>` keeps a name deliberately, so the exemption is
a line in a diff somebody reviews.

The class prefixes each theme namespace feeds are derived from the project's own
Tailwind, not listed — so a colour named `cover` is reported against `bg-cover`,
a prefix its name gives no hint of.

### `generate-types` and Tailwind v3

`generate-types` reads a v3 `tailwind.config.js` through Tailwind's own `resolveConfig`. Tailwind v3 is an optional peer of `@csszyx/cli` — 12 MB across 37 packages that only this command touches — and no package manager warns when an optional peer is missing, so the command checks before it reads a config — and before it reports that it found none, since a v4 project has none by design — and stops with one of three messages. Each is the whole explanation, printed under a `❌` prefix.

No Tailwind at all:

```text
generate-types needs Tailwind CSS v3, and this project has none installed. This command turns a v3 JavaScript config into TypeScript declarations, and reading that config is Tailwind's own job — the command calls Tailwind's resolveConfig to do it. With no Tailwind installed there is nothing to call, so it stops here rather than guessing at your theme. Install it next to the config: npm install -D tailwindcss@3 / pnpm add -D tailwindcss@3 / yarn add -D tailwindcss@3. Why it was not installed for you: Tailwind v3 pulls in 12 MB across 37 packages, and generate-types is the only csszyx command that touches it. Shipping it as a hard dependency would put those 12 MB into every install of @csszyx/cli — including a CI runner that only ever runs csszyx check. It is declared as an optional peer instead, so it arrives when you ask for this command and not before. If your project is on Tailwind v4 there is no tailwind.config.js for this command to read: v4 moved the theme into CSS (@theme { … }). Do not install v3 to get past this message — you do not need generate-types at all.
```

Tailwind is installed, but it is v4 (or any major other than 3):

```text
generate-types needs Tailwind CSS v3, and this project has {version}. Nothing is broken. This command exists to read a v3 JavaScript config (tailwind.config.js) out of an older project, and Tailwind v4 removed both that config format and the resolveConfig helper the command calls. There is no version of generate-types that works against a v4 install. On v4 the theme lives in CSS and needs no generated declarations: @import "tailwindcss"; @theme { --color-brand: oklch(0.7 0.15 250); }. If you are part-way through migrating and still have a v3 tailwind.config.js you want typed, run the command in an environment that has v3 rather than downgrading this project: npx -p tailwindcss@3 -p @csszyx/cli csszyx generate-types --config ./tailwind.config.js. Why csszyx did not install v3 for you: it is 12 MB across 37 packages for one command, so it is an optional peer rather than a dependency.
```

v3 is installed and its entry did not load — a patched copy, a blocked `exports` map, a damaged file:

```text
generate-types found Tailwind CSS {version} but could not load its resolveConfig entry: {reason}. The version is right, so this is not a missing install — the package is there and the entry point it advertises did not load. A reinstall usually clears it: npm install --force tailwindcss@3 / pnpm add -D tailwindcss@3. If it persists, the config cannot be read and generate-types has nothing to generate from. Open an issue with the version above and this line.
```

The same three sentences are thrown as an `Error` from `scanTailwindConfig` when it is called as a library, so a host such as the MCP server shows the explanation rather than a bare resolver error. `csszyx doctor` reports the state under `🧰 Optional tooling` as a line that never counts as an issue: `generate-types available (tailwindcss {version})`, `generate-types unavailable — tailwindcss v3 is an optional peer and is not installed. Only needed to read a v3 tailwind.config.js.`, `generate-types unavailable — tailwindcss {version} has no JavaScript config to read. Not needed on v4.`, or — as a warning, since a reinstall is due — `generate-types unavailable — tailwindcss {version} is installed but its resolveConfig entry did not load: {reason}. Reinstall it: npm install --force tailwindcss@3`.

A theme token that resolves to a bare RGB triplet cannot be dimmed by

The run exits non-zero rather than reporting a clean pass over the files it did

### Running it in CI

`csszyx check` is the command to gate CI on. A production build is the build CI
usually runs, and it prints `info` findings only as a count; `check` lowers every
source file the same way the build does and lists each finding with its file and
line, whatever `NODE_ENV` says.

Every finding has a level — `info`, `warn` or `error` — from
[`csszyx.config`](/docs/reference/config/#csszyxconfig). The run exits 1 when
at least one finding is `error`, or when the run itself failed: files that could
not be read, a stylesheet that would not compile, a config with an id it does
not know. `info` and `warn` findings are reported and the run still passes.

```yaml
# .github/workflows/ci.yml
- name: csszyx
  run: npx csszyx check
```

Under the default `recommended` preset every finding fails the run except the
ones that report a choice or an audit rather than a mistake. `info`:
`class-precedence` says `sz` wins over a runtime `className`, `duplicate-sz`
says which order two `sz` attributes merged in, and `merge-covered-key` and
`merge-covered-class` say what a merge removed. `warn`:
`merge-classifier-unavailable`, where every class is kept and the output is only
less merged. The preset also makes `fallback-nudge` and
`mangle-vars-hoist-skipped` `info`, but neither is a `check` finding. To fail on
any of them, set it to `error` in `csszyx.config`, or pass `--fail-on info`;
`--fail-on warn` fails on `warn` and `error` findings. Add `--json` when a later step reads the findings, for
example to annotate a pull request; the exit code is the same.

### Running it as a git hook

`--files` takes the paths a hook hands over, instead of a glob, and `--json`
replaces the prose with one parseable document. The exit code is the same
either way, so the format can change without changing what failing means.

```yaml
# lefthook.yml
pre-commit:
  commands:
    csszyx:
      glob: "*.{jsx,tsx}"
      run: npx csszyx check --files {staged_files}
```

Scoping to a subset is sound because the scan lowers each file on its own, with
no cross-module registry: a file checked alone yields exactly what it yields in
a whole-project run. Paths that are not `.jsx`/`.tsx` are dropped rather than
refused, so a README staged alongside a component does not fail the hook.

A path that *is* a source file and still cannot be read is the opposite case,
and fails the run. Counting it as scanned is how the command came to print
`No sz issues found across 1 files` for a file it never opened — the one answer
a commit gate must never give. Separators are normalised first, so a hook that
hands over `src\App.tsx` on Windows checks that file rather than reporting a
clean result for a name that exists nowhere.

The JSON document is
`{ "$schema": "https://csszyx.com/schemas/check-v2.json", "version": 2, "findings": [...] }`,
one entry per finding. The [schema](https://csszyx.com/schemas/check-v2.json)
describes every field; validate against it when a later step depends on the
shape.

```json
{
  "rule": "sibling-keyword",
  "file": "src/App.tsx",
  "line": 12,
  "message": "color: 'balance' emits text-balance, which sets text-wrap — not what color sets.",
  "kind": "sibling-keyword",
  "level": "error"
}
```

An `sz-diagnostic` finding carries the main sentence as `message`, and the
clauses the terminal prints after `help:` and `note:` as `help` and `note`,
each left out when the diagnostic has none. None of the three holds a line
break or a label. `column` is 1-based, in UTF-16 code units; `args` holds the
values the sentence names; `url` is the kind's page.

```json
{
  "rule": "sz-diagnostic",
  "kind": "unknown-key",
  "file": "src/App.tsx",
  "line": 1,
  "column": 35,
  "message": "`workBreak` is not an sz property.",
  "help": "write `break` if you meant it; for a custom utility, define it with Tailwind's `@utility`.",
  "note": "the class is still emitted, and it styles nothing unless Tailwind serves that utility.",
  "suggestion": "break",
  "args": { "key": "workBreak", "suggestion": "break" },
  "url": "https://csszyx.com/e/unknown-key",
  "level": "error"
}
```

`level` is the level the project's config gives the finding. A finding set to
`off` is not in the document.

`rule` is one of `sz-diagnostic`, `dead-class`, `broken-opacity`,
`sibling-keyword`, `theme-collision`, `merge-covered-key`,
`merge-covered-class`. It is a stable id on purpose: messages get rewritten
whenever they can be made clearer, so anything filtering on wording would break
each time one was.

`merge-covered-key` and `merge-covered-class` are an audit, not a problem: they
list each class the build drops because a later one on the same element covers
it — a later key in one static `sz` object, or an `sz` class over a static
`className` — one finding per removed class, with the line and the key it was
written as. They run when named with `--rule`, or when `csszyx.config` sets
them to `warn` or louder (the `atomic` preset does). Their findings are `info`
under `recommended`, so they fail the run only where the config sets them to
`error`:

```bash
csszyx check --rule merge-covered-key --rule merge-covered-class
```

`kind` says what an `sz-diagnostic` found: `unknown-key`, `canonical-key`,
`removed-key`, `numeric-key`, `closed-enum-value`, `slash-opacity-string`, `color-slash-opacity`, `off-scale-value`,
`numeric-font-weight`, `per-side-border-style`, `property-object`,
`non-variant-object`, `unknown-field`, `runtime-value`, `unresolvable-spread`,
`style-override`, `szs-slot-map`, `sz-recover`, `class-precedence`,
`duplicate-sz`, `spread-split-class`, `moved-value`, `global-before-group`,
`runtime-family-conflict`, `merge-classifier-unavailable`, `parse-error`,
`nesting-depth`, `unsupported-dynamic-sz` or `ast-budget`. The engine gives
every diagnostic its kind, so `other` never comes back for one; it is kept
only as an id `--rule`, `--ignore-rule` and `rules` still accept, with a
warning. Every other pass repeats its `rule`,
but for three kinds of `dead-class`: `unsigned-value`, a dead class whose sign
the project's Tailwind serves no negative for, `unserved-variant`, a dead
class whose variant the project's Tailwind does not serve, and
`prefix-disagreement`.
`fallback-missing-css` is listed too: its classes were never collected, so
they have no CSS. The fallback that still collected its classes
(`fallback-nudge`) and the `mangleVars` hoist note
(`mangle-vars-hoist-skipped`) are not `check` findings, so they never appear
here.

An `unknown-key` finding also carries `suggestion` when one known key is a
single edit away — two for a key of twelve letters or more — and the prose
report, the build and the dev server print ``help: write `{key}` if you meant it``
under the diagnostic. A swap of two neighbouring letters counts as one edit, and an alias
suggests its canonical key, so `workBreak` suggests `break`. Nothing is
rewritten, and a key with no single near match gets no suggestion, so a class a
project serves with `@utility` is not second-guessed.

`--rule <id>` keeps only the findings of that rule or kind, and
`--ignore-rule <id>` leaves them out; both repeat, and both change the exit code
as well as the report. They select findings and never set a level: a selected
`info` finding still passes. An id that is neither a
rule nor a kind fails the run rather than selecting nothing:

```text
[csszyx] ✖ {given} is not a rule or a diagnostic kind, so it would select nothing. Known ids: {ids}.
```

```text
✖ The Tailwind entries in this project set different prefixes ({file}: {prefix(name) or no prefix}; …), so sz cannot be checked against all of them. Give every entry the same @import "tailwindcss" line.
```

A `dead-class` finding of kind `prefix-disagreement`, and exit code 1: every
class is dead under one of the prefixes, so there is no answer to report. The
check skips the same build output the build walk does (`dist`, `build`,
`target`, `coverage`, `storybook-static` and the framework caches), so a stale
copy there does not cause it. `--ignore-rule prefix-disagreement` leaves the
finding out, and the dead-class pass is skipped instead of run under a guess:

```text
Dead-class check skipped: the Tailwind entries set different prefixes, and --ignore-rule prefix-disagreement left that finding out.
```

`npx @csszyx/cli scan-collisions` finds class names that would collide with a
mangled token:


```text
{n} class name(s) could collide with a mangled token:
  .{name}  (selector declared in {where})

These files declare the selectors; the class may be emitted elsewhere,
  such as a shared component, so find where the class is emitted before renaming.

Preferred: rename the class where it is declared and where it is emitted,
  to something specific (e.g. `.x` → `.resize-handle-x`) — short names

For names in a third-party stylesheet you cannot edit, reserve them:
  production: { mangle: true, mangleExclude: ["{name}"] }
```

The scan reads stylesheets only, so the files it lists are where each selector
is declared. In a monorepo the class is often emitted by a component in another
package; rename it there too, or the component keeps emitting a name the renamed
rule no longer matches.

`npx @csszyx/cli doctor` checks the install itself: `✨ No issues found! Your

## Runtime helpers

Errors from `@csszyx/runtime`, met while a page runs rather than while it builds.

```text
[csszyx] lowering-not-loaded: A string helper received an sz object, but the module that turns sz objects into class names is not loaded, so it cannot produce class names for it.
  help: add `import '@csszyx/runtime/lowering';` once at startup when the code runs outside the csszyx bundler plugin, such as in unit tests or scripts; the plugin loads it for files that can pass objects at runtime.
```

The message names the fix. It appears in unit tests and standalone scripts,
where nothing has run the plugin that would have injected the import.

```text
[csszyx] lite-sz-object: `{fnName}()` takes class strings and received the plain object `{received}`, because the compiler could not resolve this `sz` prop at build time.
  help: write `sz={[cond ? varA : varB, { key: 'val' }]}`; a spread of a conditional, such as `sz={{ ...(cond ? varA : varB), key: 'val' }}`, is the usual cause.
  note: a production build skips this check: `_sz` returns the object, or `[object Object]` beside other classes, and `_szMerge` throws a `TypeError`.
```

A spread of a conditional hides the shape from the compiler, so the build has
nothing to lower. Passing an array keeps both branches visible and csszyx merges
them.

The class toolkit refuses a selector it cannot act on, in development, and
answers as if nothing matched:

```text
[csszyx] split-box-selector-invalid: `has`, `pick` and `omit` take one selector, so an array matches nothing.
  help: pass the selectors one at a time; `splitBox` takes a list in `inner` and `outer`.
```

```text
[csszyx] split-box-selector-invalid: The empty selector `{}` names no category, so it matches nothing.
  help: name a category and a value, such as `{ overflow: "hidden" }`.
```

```text
[csszyx] split-box-unknown-category: `{name}` is not a category or class prefix csszyx knows, so it matches nothing.
  help: use the category `{hint}`.
```

When the word is also a property the qualified form can name — `color` is
the usual one — the hint offers that form beside the category, because the
category alone would catch more than the word meant: `'text'` also matches
`text-sm`.

```text
[csszyx] split-box-unknown-category: `{name}` is not a category or class prefix csszyx knows, so it matches nothing.
  help: use the category `{hint}`, or `{hint}:{name}` to match that property only.
```

```text
[csszyx] split-box-unknown-category: `{name}` is not a category or class prefix csszyx knows, so it matches nothing.
  help: call `classify('<a class>')` to see the category a class belongs to.
```

```text
[csszyx] split-box-selector-invalid: An object selector names one category and value, so `{ {categories} }` can never match a single token.
  help: pass one selector per category.
```

An empty object used to match every csszyx token, and a misspelt category
answered `false` in a way that read as "no such class". The unknown-name
message carries the category when the word is a CSS property people reach for
(`width` and `height` are `sizing`, `color` is `text`, `background` is `bg`,
`cursor` is `interaction`); for any other word, `classify('p-4')` and friends
show which category a class belongs to. The same checks run for `hasSz`,
`pickSz`, `omitSz` and `splitBoxSz`, where an sz key such as `minW` is a valid
selector.

Two helpers take two different inputs, and mixing them up says so, with a
`TypeError` in development:

```text
[csszyx] split-box-sz-string: `splitBoxSz` partitions sz objects, not class strings, so it cannot split `{value}`.
  help: use `splitBox()` for a class string.
  note: a production build drops the string instead of throwing.
```

`splitBox` takes a class string; `splitBoxSz` takes an `sz` object.

### A qualified selector reached the sz twins

```text
[csszyx] split-box-selector-invalid: `{selector}` names a property, and `hasSz`, `pickSz` and `omitSz` match an sz key by category only, so it matches nothing.
  help: pass `{name}`.
```

`'text:color'` qualifies a *class* selector by the property its value names —
`text-red-500` is a colour, `text-sm` a size. An sz key is a property already
(`color`, `text`), so there is no value to classify and the form means
nothing on `hasSz`, `pickSz`, `omitSz` and `splitBoxSz`. The message says what
to pass instead of pretending the selector does not exist.

### A peer rule kept a class on the frame

```text
[csszyx] split-box-peer-on-frame: `splitBox` keeps `{token}` on the frame although `{base}` belongs inside, because a peer rule reaches siblings and the content node is a child of the frame, where it could never match.
  help: target the content from the frame instead: `{reaching}`.
```

Every `peer-*` variant compiles to the general sibling combinator — the rule
for `peer-hover:p-4` matches an element that is a *following sibling* of the
hovered `.peer`. The frame is that sibling; the content node is a child of the
frame, so a rule placed there can never match, and `not-peer-*` there is worse:
the negation of a match that cannot happen is always true, so the class is
permanently on. `splitBox` therefore keeps every `peer-*` utility on the frame
whatever side its base belongs to, and says so once when that moved it —
`peer-checked:bg-red-500` was going outside anyway and stays quiet.

The help line names the one way to get the effect onto the content: an
arbitrary child variant on the frame, `peer-hover:[&>*]:p-4`, which Tailwind
compiles to the sibling rule followed by `> *`. `group-*`, `has-*` and `in-*`
are not affected — their rules reach descendants, and the content node is one.

### `css` went to the fallback node

```text
[csszyx] split-box-unclassified: The `css` key holds raw CSS `splitBoxSz` does not classify, so it went to the {node} node with everything else it could not classify.
  help: if its declarations belong on the other node, place it yourself with `{ {side}: ['css'] }`.
```

`css` carries raw declarations, not sz keys, so `splitBoxSz` cannot tell which
node each one belongs to. It keeps the whole object together on the fallback
node — the frame by default, the content node with `fallback: 'inner'` — as
`splitBox` does with the `[property:value]` classes it emits, rather than split
it by declaration name. Naming `css` in `inner` or `outer` places it and
silences the warning.

### A qualified selector names a property csszyx does not tell apart

```text
[csszyx] split-box-selector-invalid: `{property}` is not a property csszyx tells apart, so `{selector}` matches nothing.
  help: use one of: {properties}; `classify('<a class>')` shows the one a class carries.
```

A selector such as `'text:color'` reads the half after the colon as a
property, and the toolkit only knows the eighteen it distinguishes itself:
`align`, `attachment`, `clip`, `color`, `direction`, `family`, `image`,
`origin`, `overflow`, `position`, `repeat`, `shorthand`, `size`, `style`,
`thickness`, `weight`, `width` and `wrap`. Anything else — `colour`, `paint`,
`fontSize` — would have matched nothing silently, which is worse than the
category half being wrong, because that half already warns. The message
lists the set so the fix is a lookup rather than a search.

### A split that cannot do what the className asked for

`splitBox` routes every token correctly and the result still cannot work, in
three shapes. Each is silent in the DOM — the classes are all present — so the
warning is the only place it is said. Development only, once per message, and
none of them changes the output.

```text
[csszyx] split-box-unbounded-scroll: `splitBox` put `{scroller}` on the content node, but nothing bounds the height of either node, so the content grows instead of scrolling.
  help: give the className a height bound such as `h-64`, `max-h-96` or `h-full`, or put `flex flex-col min-h-0` on the frame and `flex-1 min-h-0` on the content.
```

A scroll container with no height grows to fit its content, so it never
scrolls. The bound can be a class on either node (`h-*`, `max-h-*`, `min-h-*`,
`size-*`) or it can come from the parent, which is why an absolutely positioned
frame and a flex child (`flex-1`, `grow`, `basis-*`) are accepted as bounded.

```text
[csszyx] split-box-unclipped-corners: The `splitBox` frame is rounded and the content scrolls, but the frame does not clip, so scrolled content paints over the corners.
  help: add `overflow-hidden` to the frame.
```

Scrolled content paints out to the padding box, so it runs over a corner the
frame rounded but never clipped.

```text
[csszyx] split-box-hidden-content: `splitBox` put `{hidden}` on the content node, so the frame keeps its background, border and size and stays visible.
  help: pass `{ outer: ['hidden'] }` if the whole box should disappear.
```

`hidden` is `display: none`, which acts on the contents, so it stops the content
node from rendering while the frame keeps painting. Under a variant the pair is
usually deliberate — `hidden md:block` toggles the content on purpose — so only
the bare form is named.

These three read the class buckets, so they do not fire for `splitBoxSz`, which
partitions an sz object.

### A class csszyx does not recognise

```text
[csszyx] split-box-unclassified: `{token}` is not a utility csszyx knows, so it went to the {node} node with everything else it could not classify.
  help: if it is a custom `@utility` that declares properties for both nodes, place it yourself with `{ {side}: ['{token}'] }`; csszyx cannot split it, and no side is correct.
```

The toolkit's vocabulary is atomic utilities — a class whose name states one
feature. A custom `@utility` that declares several properties at once has no
correct side: send it outward and the content loses the padding it declared,
inward and the margin moves inside the frame, to both and the margin applies
twice while the background paints twice. csszyx will not rewrite your CSS into
per-property fragments to make the question answerable, so it says what it did
and hands the call back.

`{node}` is the node the fallback chose — `frame` by default, `content` when
you passed `fallback: 'inner'` — and `{side}` is the opposite one, so the help
line always suggests moving the class rather than leaving it where it is.

Placing the token by hand is the fix, and a placement list accepts the literal
class name for exactly this case — `{ inner: ['card'] }` works even though
`card` is in no category. It is matched as a whole name, never as a prefix of
`card-lg`, because csszyx knows nothing about an unrecognised token's
structure, and it is the name you WROTE even on a mangled build, since the
token is decoded before the comparison.

A placement list therefore does not report an unknown base name: it can name
a literal class, and one options object usually serves many classNames, so a
render without that class is not a mistake. `has`, `pick` and `omit` are the
other way round — there the string IS the query, so an unknown one is still
reported as the typo it usually is.

The message also never fires for a token you placed yourself, including onto
the side the fallback would have chosen anyway.

### A placement names a variant

```text
[csszyx] split-box-placement-variant: A `splitBox` placement list names a class by its base, so `{selector}` never matches: the variant prefix and the `!` or `-` marker are stripped before the comparison.
  help: write `{ {side}: ['{base}'] }`; it places every variant of `{base}`.
```

Use the base name in `outer` and `inner` placement lists. The rule applies to
every variant of that base, so `{ outer: ['hidden'] }` also places
`hover:hidden` and bare `hidden` on the frame. Selecting only `md:hidden`
is not supported, and neither is the important or negative form — `!hidden`
and `-mt-4` normalise to `hidden` and `mt-4` before the comparison, and the
message names that form. This development warning leaves routing unchanged;
update the placement to make it take effect.

See [Override the defaults](/docs/box-model-splitbox/#override-the-defaults)
for literal custom-class placement, and
[Categories](/docs/box-model-splitbox/#categories) for recognised selectors.

### The cap on development warnings

```text
[csszyx] diagnostics-capped: This session has printed {count} distinct development warnings, so further ones are suppressed.
  help: look above for one warning repeating with different values; a className built from data is the usual cause.
```

Every warning prints once per distinct message, and the cache behind that
holds at most 512 of them. Several messages interpolate a class name from your
own className, so a class built from data — `user-data-42`, one per row —
would otherwise make every render a new message and the cache grow for as long
as the dev server runs. Rather than go quiet when it fills, the cache says so,
once: the line above replaces the first message it would have dropped. A
warning that repeats above it with different values names the component to
look at. Production is unaffected; no warning is emitted there at all.

## Framework adapters

A Vue or Svelte template has no csszyx runtime, so the adapters write a class
only for an `sz` value the engine resolves completely at build time. Any other
value is an error, its attribute is left as written, and the build stops. Both
messages start with the file and the position of the value in it:

| Message | When |
| --- | --- |
| ``[csszyx] {file}:{line}:{col}: this sz value is only known at runtime, and a template has no csszyx runtime to resolve it`` | a name, a prop, a conditional, a call, an array value, or a template string with `${}` |
| ``[csszyx] {file}:{line}:{col}: this sz value could not be parsed as a JavaScript expression`` | a syntax error in the value |
| ``[csszyx] {file}:{line}:{col}: Vue cannot parse this file, so no sz in it gets a class: {reason}`` | `vue/compiler-sfc` rejects the file, an element left open say |
| ``[csszyx] {file}:{line}:{col}: Svelte cannot parse this file, so no sz in it gets a class: {reason}`` | `svelte/compiler` rejects the component: the quoted `sz="{ p: 4 }"`, TypeScript without `lang="ts"`, or markup another preprocessor has not turned into Svelte yet |
| ``[csszyx] {file}:{line}:{col}: csszyx reads sz in an HTML template only, and this one is <template lang="{lang}">`` | a Vue template in another language, such as pug |
| ``[csszyx] {file}:1:1: csszyx reads Svelte 5 markup, and svelte {version} resolves`` | the project installs Svelte 4 |
| ``[csszyx] {adapter} reads templates with `{parser}`, which does not resolve from it help: install {package} in the project`` (the `help:` on its own line) | the project does not install `vue` or `svelte` |

The first is followed by `help: write the value as a literal, e.g. { p: 4 }, or
bind class or style yourself for a value that changes at runtime`, and both by
`note: the attribute is left as written; no class is generated for it`. A file
the framework's parser rejects is one error, and no `sz` in it is lowered; its
`help:` line says what to change: write `sz={{ p: 4 }}`, or run csszyx after the
preprocessors that turn the file into Svelte.

An adapter loads its framework's parser from the project the first time a file
needs it. When none resolves, the build stops on:

```text
[csszyx] @csszyx/vue-adapter reads templates with `vue/compiler-sfc`, which does not resolve from it
help: install vue@3.5 in the project
```

The Svelte adapter names `svelte/compiler` and `svelte@5` the same way. The
engine's warnings for a value that did lower, such as an unknown key, are
reported at the same kind of position as warnings.

The Vite plugins and `@csszyx/unplugin` fail the build on an error and pass
warnings to the bundler. The Svelte preprocessor throws with every error of the
file and prints warnings. `preprocess()` from either adapter reports nothing
itself: it returns them in `result.diagnostics`.

## One engine, two artifacts

csszyx compiles with ONE engine that ships as two artifacts, selected by
`build.parser`: `rust` (the native addon, the default) and `wasm` (the same
engine compiled to WebAssembly, shipped inside `@csszyx/core` — also the
automatic fallback when the native binary is absent). Because both are
compilations of the same source, their classes, code and diagnostics are
identical; the frozen parse corpus and a per-PR full-build smoke pin that
byte for byte.

Upgrading from a version that still had the TypeScript engines (`'oxc'` /
`'babel'` values): those lanes deferred a const the file declares to a runtime
CSS variable where the engine reads it at build time (`const x = 4` then
`sz={{ p: x }}` now compiles to `p-4`), and Babel emitted an identifier-named
class for a computed key (`k-4`) where the engine emits none. The engine's
answers were the intended ones; the pinned expectations moved with it.

### The compiler and the engine come from different releases

```text
[csszyx] engine-version-skew: @csszyx/compiler {version} was built for engine source {digest} and found {engine}
help: install @csszyx/core@{version}; it installs its platform package at the same version
```

The `help:` line names the fix for what answered:

```text
help: install @csszyx/core@{version}; {platformPackage} must be {version} too, so reinstall it if your lockfile holds another version
help: rebuild the engine from this checkout with `pnpm --filter @csszyx/core {task}` after changing its source
```

The first is for the native engine of another release: a lockfile can keep an
older platform package beside a current `@csszyx/core`. The second is for an
engine at the compiler's version built from other source, which happens only
in a checkout of csszyx itself; `{task}` is `native:build` for the native
engine and `build` for wasm.

`{engine}` names the artifact and what it reported, such as `the native
(@csszyx/core-linux-x64-gnu) engine 0.17.2 (source 9b40c2d1e7a35f08)`, or says it
comes from a release before 0.18 that does not report its version.

`@csszyx/compiler` and the engine in `@csszyx/core` are released together but
installed apart, so a lockfile or a cache can pair them across releases. An
engine from another release ignores options it does not know and lowers with
other tables, so the first call into either artifact checks the version and the
digest of the engine's source, and the build stops on a mismatch. There is no
setting that skips the check. Install `@csszyx/core` at the compiler's version;
`@csszyx/unplugin`, `@csszyx/cli` and `csszyx` pin it for you. When both sides
report the same version, the engine and the compiler were built from different
checkouts of csszyx itself: rebuild the engine.

### The plugin and the runtime come from different releases

```text
[csszyx] runtime-version-skew: @csszyx/unplugin {pluginVersion} found @csszyx/runtime {runtimeVersion} at {runtimeDir}
help: install @csszyx/runtime@{pluginVersion}; the build and the runtime lower sz objects with rules from the same release
```

The build lowers every static `sz` object, and `@csszyx/runtime` lowers the rest
in the browser — `szr`, `szv`, objects built at run time — and merges classes
with the table the build wrote. Each side carries its own copy of the rules, so a
runtime from another release writes other classes for the same object, and
neither output says so. The plugin reads the `@csszyx/runtime` your project
root resolves when the build starts (on Turbopack, in `csszyx next prebuild` and
in the loader) and stops when its version differs. A package that pins its own
copy of the runtime is not compared. Install the runtime at the plugin's
version; with pnpm, `pnpm why @csszyx/runtime` shows which package pulled in the
other copy.

command's dead-class pass tells you which one.
</Aside>
